Review order

1. Public surface and exposed internals

BH-P05 and BH-031 are the two most important issues because they sit on public or semi-public edges and can be abused without much setup.

2. Save-flow resilience

BH-006 and BH-009 are the most user-hostile daily workflow bugs: users type real data, hit one validation problem, and lose context or get no error signal.

3. Export / storage contract

BH-025 + BH-026 are one operator journey, and BH-023 is the deeper contract bug behind the alt-filesystem story.

4. Data integrity before polish

BH-011, BH-020, BH-024, and BH-018 all allow bad or misleading state to persist and then fan out into secondary UI defects.

Deduped chains

BH-025 + BH-026

BH-011 -> BH-008

Broken image ingest is the upstream defect. The invisible crop overlay is the downstream symptom that users actually see.

BH-020 + BH-024

BH-024 is the table/query branch of the bigger "dangling IDs remain in block content" problem.

BH-023

Not three separate bugs. It is one half-wired feature with three broken layers: create UI, multipart API, and archive contract.

BH-005

The raw claim looks stale on case sensitivity. Current search code and tests are case-insensitive, so only the typo-tolerance angle still looks like a live product gap.

Truth maintenance

BH-032 needs a narrower fix description.

The missing-header issue is still real, but the raw log's token-leak example via Google Fonts looks stale. The current templates/shared/base.tpl does not load external fonts, so the share-token leak mechanism should be re-checked while implementing the header middleware.

BH-005 should not be treated as a confirmed bug.

Current search code lowercases cache keys, computes case-insensitive relevance, and has tests for case-insensitive prefix matching. Keep the fuzzy-search request as a feature gap, not as a proven regression.

Public surface and exposed internals

5 bugs grouped here: fix these before broader polish because they touch public URLs, raw uploads, and error serialization.

High lane

BH-P05 BH-031 BH-034 BH-032 BH-033

These five issues all live on boundaries where mistakes are expensive: public share links, unauthenticated JSON error routes, and unbounded multipart uploads. This is the cleanest place to start because the fixes are easy to explain in review and reduce a lot of downstream risk.

Code notes

  • server/template_handlers/render_template.go strips several internal fields for .json responses, but it still leaves _appContext and _requestContext in the serialized context. That lines up with BH-P05.
  • server/share_server.go starts a raw mux.Router with no share-specific hardening middleware, so BH-032 still has a real foundation.
  • handleBlockStateUpdate in server/share_server.go verifies token validity and note membership, then writes state immediately. There is no block-type allowlist, which matches BH-031.
  • server/template_handlers/template_context_providers/note_template_context.go still builds shareBaseUrl straight from ShareBindAddress and SharePort, which keeps BH-033 alive.
  • server/api_handlers/version_api_handlers.go and server/api_handlers/resource_api_handlers.go still parse multipart bodies without http.MaxBytesReader, while server/api_handlers/import_api_handlers.go shows the correct pattern.
Implementation note

BH-P05 and BH-031 are the two bugs to pair in the first hardening pass. BH-032, BH-033, and BH-034 fit naturally behind them in the same review since they touch the same boundary code.

Export, import, and storage contract

6 bugs grouped here: one operator journey plus the alt-filesystem contract that can silently drift data onto the wrong backend.

High lane

BH-025 BH-026 BH-023 BH-016 BH-017 BH-015

This group is best reviewed as one story: start an export, reload, try to recover from the jobs panel, then archive and re-import. Right now each hop drops important context.

Code notes

  • src/components/adminExport.js restores only selected groups in init(). It never reconnects to SSE or restores this.job unless submit() was just called, which confirms BH-025.
  • templates/partials/downloadCockpit.tpl only shows completion-time links for job.resourceId and plugin-action redirects. There is still no branch for completed group-export jobs, which confirms BH-026.
  • src/components/downloadCockpit.js and templates/adminExport.tpl both still display uncapped progressPercent, which matches BH-015.
  • archive/manifest.go still has no storage_location field in ResourcePayload, so BH-023's archive-loss claim still stands.
  • models/query_models/resource_query.go still omits PathName from ResourceCreator, and templates/createResource.tpl still has no storage selector while templates/adminOverview.tpl advertises available alt filesystems.
  • application_context/import_plan.go and templates/adminImport.tpl still report only created/skipped counters, not merged or GUID-relinked outcomes, which preserves BH-016.
Implementation note

Review BH-025 + BH-026 together as one fix set. BH-023 is the deeper contract bug here; if it waits, any alt-filesystem feature work remains risky.

Validation and save-flow resilience

3 bugs grouped here: this is the "user typed data and the UI did not help" lane.

High lane

BH-006 BH-009 BH-010

These three bugs belong together because they all erode trust in form submission: the app either navigates away from the form, blocks the save silently, or seeds obviously wrong data into preview.

Code notes

  • templates/createResource.tpl is still a native <form method="post">, which is consistent with the state-loss pattern reported in BH-006. The report says that same pattern appears across the create/edit flows.
  • src/schema-editor/modes/form-mode.ts still checks only min/max string and numeric bounds in its blur handlers. There is no valueMissing or patternMismatch branch, which keeps BH-009 alive.
  • The preview path still accepts a real numeric 0 as input; the renderer itself only shows empty when the harness does not preseed the field. That means BH-010 is still most likely a preview-state bug, not a renderer-only bug.
Implementation note

BH-006 and BH-009 should be reviewed in the same pass because both are "submit failed but the page did not guide me" defects. BH-010 is a natural add-on while someone is already in schema-form preview code.

Data integrity and stale references

6 bugs grouped here: corrupt or half-valid state gets stored, then shows up later as broken crop flows, bad matches, or 500s.

Medium lane

BH-011 BH-008 BH-020 BH-024 BH-018 BH-019

This is the most "compounding effects" cluster in the report. The same bad rows can create broken crop behavior, stale table queries, misleading similarity suggestions, and invisible cleanup debt.

Code notes

  • src/components/imageCropper.js still hides the visual selection overlay when natural dimensions are zero, while submit only checks the stored rectangle. That makes BH-008 a downstream symptom of BH-011, not a root cause on its own.
  • hash_worker/worker.go still computes both AHash and DHash, stores both, but only caches and compares DHash for similarity lookups. That keeps BH-018 alive exactly as logged.
  • server/api_handlers/block_api_handlers.go still returns 500 on RunReadOnlyQuery failure in the table-block handler instead of routing nested not-found errors through statusCodeForError, which confirms BH-024.
  • The raw log's bigger stale-reference story still makes sense: BH-024 is the table branch of BH-020, and nothing I spot-checked suggests automatic cleanup was added for embedded block IDs.
  • BH-019 was not re-executed here, but it still belongs in this cluster because the consequence is stored invalid data that can later poison exports, logs, or downstream tooling.
Implementation note

Fix BH-011 before spending much energy on BH-008. Review BH-020 and BH-024 together. BH-018 matters more than it looks because the merge action it feeds is destructive.

Accessibility on core workflows

4 bugs grouped here: separate audits, same outcome. Core workflows look fine visually but are under-described semantically.

High lane

BH-027 BH-028 BH-029 BH-030

These belong together because they all need the same style of review: keyboard support, semantic roles, and explicit text alternatives instead of visual-only cues.

Code notes

  • templates/partials/downloadCockpit.tpl still has no dialog role on the panel container, no ARIA progressbar semantics, and only a title attribute on the connection dot. The underlying component also does not move focus on open.
  • templates/partials/blockEditor.tpl still shows gallery images without alt, a heading-level <select> without a label, icon buttons that depend on title, and an add-block picker with no disclosure roles.
  • src/components/groupTree.js still builds a visual tree out of plain <ul>/<li> elements and click handlers. There is still no ARIA tree model or arrow-key roving focus.
  • templates/partials/compareImage.tpl still declares a radiogroup with radio buttons but does not implement the expected keyboard pattern or roving tabindex.
Implementation note

BH-027 and BH-028 are the best first accessibility targets because they affect authoring and recovery surfaces directly. BH-029 and BH-030 are still worth fixing, but they can follow that first pass.

MRQL, editor maturity, and docs drift

5 bugs grouped here if you count BH-005 as re-test material: all of them affect trust in search, MRQL, or block authoring.

Medium lane

BH-012 BH-013 BH-021 BH-022 BH-005

This cluster is less about immediate breakage and more about product trust: users expect saved queries to update, large MRQL results to stay manageable, docs to match live routes, and the block editor to support common text syntax.

Code notes

  • src/components/mrqlEditor.js still posts to /v1/mrql/saved for save actions and never switches to PUT for update. BH-012 remains straightforward.
  • server/routes.go still registers live MRQL and editMeta endpoints, while server/routes_openapi.go still lacks those registrations. That keeps BH-022 confirmed.
  • src/components/blockEditor.js still supports only **bold**, *italic*, and links in renderMarkdown(). BH-021 remains accurate.
  • BH-013 was not re-run here, but it still fits this review lane because it is about MRQL result safety at scale rather than isolated UI polish.
  • For BH-005, the current code and tests are case-insensitive. The raw claim should be split into two: case sensitivity looks stale; typo tolerance still looks like a feature request, not a verified defect.
Implementation note

If someone is already in MRQL, pair BH-012 and BH-022 first. BH-013 and BH-021 are good follow-ons in the same product-trust sweep.

Polish and confusing destructive UX

Low lane

BH-014 BH-007 BH-001 BH-002

These are not the bugs to lead with, but they are the sort of issues that make the product feel brittle or under-explained, especially around delete flows and metadata display.

Code notes

  • templates/partials/json.tpl still does appendChild(renderJsonTable(...)), and src/tableMaker.js still returns a string for null/undefined. BH-002 remains plausible from code alone.

Implementation note

BH-014 is the only item here with meaningful user-expectation risk. The rest fit well into a later cleanup pass.

Method and limits

I did not re-run the app, replay browser scripts, or change the canonical markdown log while making this report. The investigation here is a source-and-evidence pass only.

Anything called out as "re-check" is where the current tree no longer matches the raw log verbatim. The biggest examples are BH-032's external-request rationale and BH-005's case-sensitivity claim.
