# Documentation

Everything written about mahresources that is not the code itself. Start here.

| Path | What it holds | Authoritative? |
|---|---|---|
| [`architecture/`](architecture/) | How subsystems are actually built today. | Yes — keep current. |
| [`adr/`](adr/) | Architecture decision records: a decision, its context, and what it rules out. | Yes — append-only. |
| [`plans/`](plans/) | Design and implementation notes per feature, mostly historical. | No — see below. |
| [`ideas/`](ideas/) | Roadmap sketches for work not yet scheduled. | No. |
| [`todo.md`](todo.md) | The checklist for whatever is in flight right now. | Working file. |
| [`lessons.md`](lessons.md) | Mistakes worth not repeating, newest first. | Working file. |

## Which of these can you trust?

`architecture/` and `adr/` describe the system as it stands and are meant to be
corrected when they drift. `plans/` is a record of intent at a moment in time —
useful for *why* something looks the way it does, unreliable for *what the code
does now*. When a plan and the code disagree, the code wins.

The two working files are referenced by name from [`CLAUDE.md`](../CLAUDE.md);
if you move them, update those references.

## Adding a new document

Put it in `architecture/` if it describes how something works now, `adr/` if it
records a decision, and `plans/` if it is design or implementation notes for a
specific piece of work. Plans follow `YYYY-MM-DD-<slug>-design.md` and
`YYYY-MM-DD-<slug>-impl.md`; once the work ships, move the pair into
`plans/archive/` and re-run the index.
