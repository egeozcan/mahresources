# Plugin download pacing and deferred downloads

A plugin can narrow its own `mah.download.submit` traffic with a manifest-level `download_limits` list. It is deliberately **not** a capability and deliberately not part of consent: a throttle grants no new power, affects no other principal's jobs, and removing it only returns the plugin to the download power `db:write` already granted. `host` reuses the `network` grammar and `NetworkRule.Matches`, `api_version` is required once the key is present, and the first matching rule wins so an author can put an exact exception before a wildcard. Wrong shapes are refused by name at parse time; a typo in `concurrency` must not silently mean unlimited.

The queue gate is job-level and process-local. It sits in `download_queue`, takes no dependency on `plugin_system`, and is wired through `SetThrottleResolver` in the same late-binding shape as the plugin egress resolver. It is acquired **before** the global semaphore — including backoff and min-interval waits — because a domain that is waiting politely must not occupy one of the deployment-wide worker slots. The gate is inert at its zero value so struct-literal test managers and deployments with no declarations do not change. Its mutex is independent of `dm.mu` and `j.mu`, and it is never held while waiting, notifying, recording history or emitting job events. `min_interval` reserves its assigned start time under the lock (`lastStart = max(now, lastStart+interval)`) rather than checking and then sleeping, or two jobs can read the same old value and start together. A `429` or `503` charges backoff against the **submitted** URL's host, the key future jobs will match, not a redirected final host. `Retry-After` is honored but clamped to the declared backoff ceiling. HLS segment requests are out of scope for this gate — one HLS job may still use `-hls-concurrency`, and `hls` handles segment retries itself — and generic export/import/action jobs never enter `processJob` because they have no remote URL to key.

Deferred plugin downloads stay under `db:write` for the same reason immediate `mah.download.submit` does: one URL is fetched into the library by the host; only the start time changes, so this is not recurring unattended plugin code. `{start_at=<unix seconds>}` and `{delay="2h"}` are mutually exclusive. A relative `delay` is capped at thirty days. An absolute `start_at` must be in the future and before the year 10000 (SQLite neither parses nor text-orders a five-digit year). Both return `{scheduled=true, scheduled_id=<row id>, start_at=...}` rather than `id`, because no queue job exists yet. The row is durable and **not** resident in the in-memory queue, whose 100-job cap never evicts pending jobs. It stores the plugin name and payload, including headers, so a restart does not turn the fire into an unrestricted host fetch.

A scheduled download insert is principal-bound before `Create`, because the stamp callback overwrites `CreatedByUserId`; setting the field on the struct would be replaced by the worker/default actor. The plugin scheduler's existing ticker runs the due-row sweep after the `pm == nil` early return — without a plugin manager no plugin policy can be resolved, so no row fires, and the dispatch of a row's Job blocks it as `plugin-unavailable`. Firing claims with one conditional `UPDATE`. A row with a durable Job is then handed to that Job (`submitDeferredRowToItsJob`: reserve `status=submitted`, materialize the Job, record it; a read or write that fails there takes the reservation back, because the Job still runs and a failed row would disagree with it) and nothing else is checked there: the plugin, the stored actor's role and scope and a busy URL are decided once, by the Job's own dispatch, which the dispatch loop can reach at the due time before the sweep sees the row. A legacy row with no Job re-validates the stored actor's role and scope (resolved as a Job's dispatch resolves it, `dispatchBinding`: a read of the account, its scope or a target that fails puts the row back for a later sweep rather than failing it), checks the plugin is still available, and reserves `status=submitted` **before** calling the queue so a stale claim cannot double-submit. The cost is fail-closed: a crash between reserve and submit, or a DB failure after submit, can strand a submitted row without a job id and needs operational repair, but it will not fork the download. Owner deletion NULLs `created_by_user_id` through `stampedModels()`, and ownerless pending rows are never claimed rather than falling back to root.

A deferred download is two records, the row and a `scheduled` `deferred-download` Job, and the dispatch loop claims that Job at its `scheduled_for` without consulting the row. A cancel therefore ends both: the download adapter's `ApplyHostTransition` cancels the row inside the host cancel's transaction (the pending row, or one a sweep reserved or submitted for this Job when the Job never started; that sweep then finds its reservation lost), and `CancelScheduledDownload` cancels an unstarted Job inside its own (a started one is refused). Both take the Job's lock before the row's. "The row's Job" is always the Job the row was accepted with (`deferredDownloadJobIDOn`: its source mapping's Job), never whatever the row's legacy handle names, because a Retry moves the handle to its successor; the sweep, both cancels and startup reconciliation all use it. A row is due once its time is a millisecond behind the sweep's clock, because `julianday()` rounds to milliseconds. A Retry of a deferred download that never started is an ordinary immediate download, offered as **Download now** with a confirmation; the row stays cancelled and does not track it. A due row whose Job ended before it ran is recorded `cancelled` or `failed`, never `submitted`, and startup (`ReconcileDeferredDownloadRows`) does the same for rows earlier releases left pending, or submitted naming such a Job. A pending row whose Job retention has deleted is recorded `failed`, saying its outcome is not known, and is never submitted from its payload: retention deletes only ended Jobs, but the dispatch loop can run a Job before the sweep records its row, so a deleted Job may have run. Every reader of a row's Job goes through `loadDeferredRowJob`, and every reader of any mapped Job answers a missing one through `mappedJobGone`, so the sweep, materialization, startup reconciliation (the same rule in SQL), the row cancel (409, `ErrScheduledDownloadEnded`) and readiness cannot each decide it differently; the migration's verify, changed-source, re-arm and command-backfill paths record it as an expired replay (`expireMappingOfGoneJob`, `downloadReplayPurged`, `ensureCommandReplay`) rather than quarantining the source. Startup reconciliation reads a row's own Job through its source mapping for submitted rows too: an earlier release's sweep could write a Retry successor's id into `job_id`. Nothing rewrites a mapping's Job once it names one: the migration's changed-source refresh verifies against it and consults the legacy handle only for a mapping that names none. Due and claim times are compared as instants (`julianday()` on SQLite): a `start_at` is stored in UTC and a `delay` in the writer's zone, and SQLite compares text. The row's `JobID` is written only by the fire, possibly after the row was scrubbed, so `retiredScheduledDownloadMatches` accepts a row that differs from its post-scrub hash in a `JobID` alone where the hash recorded none. Which Job an earlier release's fire named cannot always be re-established (a Retry moved the handle, retention prunes Retry history), and it need not be: the `JobID` carries no replay material, and the payload, URL, id and plugin must still match exactly.
