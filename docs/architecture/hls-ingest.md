# HLS ingest

A fetched URL that returns an HLS playlist is assembled into one MP4 rather than stored as the few kilobytes of text that listed the media. It lives in `hls/`, a leaf package in the shape `groupio/` and `search/` established, because **two** independent fetch paths need it and neither can host it: `AddRemoteResource` (`application_context`, behind `/v1/resource/remote`, the CLI and a plugin's `create_resource_from_url`) and `downloadWithProgress` (`download_queue`, which does its own HTTP and sits *below* `application_context`). It takes its `http.Client`, ffmpeg path and limits per call, never at construction.

- **The package fetches every segment itself, through the caller's client, and ffmpeg is never given a URL.** Handing ffmpeg the playlist is a dozen lines shorter and hands it the network too: ffmpeg's HLS demuxer opens `http`, `https` and `crypto` targets named from *inside* the playlist, with none of the caller's egress policy applied to any of them — so a crafted playlist reaches `169.254.169.254` unchecked, through the exact door `-allow-private-fetch` exists to close. Instead the playlist, the key and every segment go through the client the caller already decorated: the plugin's own allowlist for a plugin fetch, the host policy otherwise. The mux runs `-protocol_whitelist file,crypto` and cannot open a socket. `TestEverySegmentGoesThroughTheCallersClient` and `TestAddRemoteResource_HLSSegmentsAreSubjectToTheFetchPolicy` are that property from both ends.
- **`Deps.CheckURL` is required, and a nil one refuses everything.** It is asked for the *submitted* URL too, not only what a playlist names: a plugin's URL was checked when it was submitted, but a retry replays a stored payload, possibly in another process and possibly after an operator narrowed that plugin's network list. The client's decoration carries layers (b) and (c) — the per-redirect re-check and the dial-time deny — but *not* layer (a), the allowlist, whose comment in `ApplyEgressPolicy` says outright that the caller applies it before the request starts. Every other caller in the tree holds exactly one URL and checks it once. A playlist names more, and none of them passed through a caller, so without this a plugin confined to `a.example` reaches any public host by being served a playlist that says to. It is asked before **every** request — variant playlist, key, init segment, each segment — and `TestEveryRequestedURLIsCheckedAgainstTheAllowlist` pins that with two servers that differ only by port.
- **Callers pass the URL the playlist was *served from*, not the one they asked for.** A redirect from `/watch` to `/cdn/abc/index.m3u8` moves the base by a whole directory, and every relative segment reference resolves against it; `fetchText` likewise returns the final URL of a nested playlist.
- **A variant naming `AUDIO="group"` carries no audio of its own.** Its tracks live in an `EXT-X-MEDIA` rendition, so downloading only the variant produces a silent video that plays perfectly — the worst failure available, since nothing looks wrong until someone listens. The rendition is fetched as a second media playlist into its own subdirectory (both number their segments from zero) and muxed as a second input with explicit `-map`s. It shares the download's byte and segment budgets rather than getting its own, or a playlist would spend twice the configured cap by splitting its streams. A rendition with no `URI` is already multiplexed into the video segments and needs nothing.
- **`EXT-X-BYTERANGE` with no `@offset` means "the byte after the previous sub-range of this resource"**, and the parser reports that as 0 — so an untracked playlist of sub-ranges fetches the *first* n bytes every time and muxes the opening fragment repeatedly. A running end is kept per URL, and applied only where the **raw text** carried no `@`: the parser represents an omitted offset and an explicit `@0` identically, they mean opposite things, and guessing either way corrupts the other, so `explicitByteRangeOffsets` scans the playlist text to tell them apart. A server that ignores `Range` and answers 200 with the whole object is sliced locally rather than stored once per sub-range.
- **The sniff's read error is checked.** `io.ReadFull` returning anything but `EOF`/`ErrUnexpectedEOF` is the transfer failing, and discarding it stored whatever had arrived as a complete resource — a connection dropped ten bytes in became a ten-byte file reported as a successful download.
- **A playlist is recognised from its bytes**, not its extension or Content-Type. The URLs this exists for are generated endpoints carrying neither. The sniff reads the head off the response, so both callers must put those bytes back for everything that is *not* a playlist — the one regression this introduces, covered at sizes below, equal to and above the sniff length in both packages.
- **Refusals, not truncation, and each says which.** A playlist with no `EXT-X-ENDLIST` is a live stream, whose sliding window would make the byte and segment caps yield an arbitrary clip rather than an answer. `SAMPLE-AES` and any non-identity `KEYFORMAT` are DRM, so the message says DRM rather than "unsupported", which a user would otherwise retry. A non-HTTP reference is refused because the fetch policy classifies *addresses*, and `file:///etc/passwd` has none. `ErrNotSupported` distinguishes all of these from a failure.
- **Neither `pl.Key` nor `pl.Map` is read; the parse is driven entirely by the segments.** The parser publishes the first of each tag twice — once on the playlist "for convenient playlist generation" and once on the segment it precedes — and `pl.Key` is set from the first `EXT-X-KEY` *wherever* it appears, so a stream that starts in the clear and turns encrypted seeded as encrypted and decrypted its clear segments. Reading both sources also consumed the raw-text explicit-offset marker twice, refusing ordinary ranged fMP4. Every `KEY` and `MAP` tag attaches to exactly one segment, in text order, so one source is both correct and simpler. Whether the initialization section is encrypted is the one thing the parse cannot answer — every tag above the first segment attaches to it, and when two keys sit there only the last survives — so `headerKeys` reads the raw text for the key in effect at the map and at the first segment. Both wrong answers produce a file that decodes to nothing without naming a cause, and a stream that protects its map with a *different* key is refused rather than assembled with the wrong one: that key is not in the parse at all.
- **A key stays in effect until another `EXT-X-KEY` replaces it**, which the parser does not express: it attaches a key only to the segment the tag preceded. Falling back to the playlist-level key for every untagged segment decrypted a rotated stream entirely with its first key — and read a mid-stream `METHOD=NONE` as "still encrypted", since that arrives as a tag whose parsed key is nil, indistinguishable from no tag unless the tag itself is tracked. The initialization section's own key is recorded and written **before** the `EXT-X-MAP` line, because ffmpeg decrypts the map with whichever key it has seen by the time it reads it.
- **Bytes are charged where they cross the network, not where they are kept.** A server that ignores `Range` and sends the whole object has its skipped prefix charged to the budget too, or a playlist of one-byte ranges at gigabyte offsets pulls down gigabytes under a one-byte cap. The key ceiling bounds the *read* rather than checking the total afterwards, so a hostile key endpoint cannot spend the whole download budget before being refused.
- **A ranged fetch must deliver exactly what it promised.** The range reader is bounded rather than checked, so a short response left the missing bytes simply absent and the mux failed opaquely. A `206` is refused unless its `Content-Range` parses and starts where the request asked; an `EXT-X-MAP` byte range with no explicit offset is refused rather than guessed, because the running offset that places media sub-ranges cannot see how the two tags interleave.
- **Every request carries the deployment's idle bound** (`Deps.IdleTimeout`), not only the one the caller opened. The overall deadline is no substitute: a server that sends headers and then stalls holds a worker for the whole of it, and a playlist has hundreds of chances to do that. The guard closes the body before waiting for its pending read, so nothing writes into the caller's buffer after the read has returned.
- **AES-128 is handled by fetching the key ourselves** through the same policed client and rewriting the local playlist to name it as a file. The local playlist is *generated* from the parsed structure rather than edited by substitution, so ffmpeg sees only tags this package validated — a substitution would carry through whatever else the origin wrote, including tags naming URLs nobody policed. `EXT-X-MEDIA-SEQUENCE` is reproduced because a key with no `IV` derives one from the sequence number, and dropping it decrypts every segment with the wrong IV and yields noise rather than an error.
- **The queue resolves the ffmpeg path per download, not at construction.** Startup auto-detects ffmpeg on `PATH` *after* the context and its download manager exist, so a captured string stayed empty in the most ordinary deployment there is — ffmpeg installed, no `-ffmpeg-path` — and every queued HLS download failed saying ffmpeg was unavailable while the boot log said it had been found. The synchronous path reads it live and worked, so the two disagreed. `ManagerConfig.FfmpegPath` is a `func() string` for that reason.
- **The segment cap bounds *parsing*, not just the result.** The parser materializes every segment it is handed, so a playlist well inside the byte limit — a million one-character entries is a few megabytes — allocates hundreds of megabytes before a check on the result could refuse it. `parse` counts `#EXTINF:` in the text first; `readMedia` still enforces the same limit on what it accepts.
- **Progress rides the queue's phase counters: segments of the total, across the video and any audio rendition, from the playlist to the end.** An HLS stream's size is unknown until the last segment lands, which is what the queue's `TotalSize: -1` already means; the playlist response's own Content-Length is reset to it once the body is recognised as a playlist. The byte counters carry the bytes received, a metric beside the segments, until the assembled file's size replaces them. The assembly reports every segment done, so the Job never changes its unit, which would drop the history its speed and graph are drawn from. Notifications are throttled at `progressNotifyInterval` like the byte progress, or a four-hundred-segment stream is four hundred SSE events; a change of phase is always sent.
- **Byte ranges are resolved by us, not passed on.** `EXT-X-BYTERANGE` becomes an HTTP `Range` header and each range lands in its own local file, so the generated playlist carries no byte-range tags.
- **The whole HLS assembly carries one deadline** (`Options.OverallTimeout`, the deployment's `-remote-overall-timeout`). `http.Client.Timeout` applies per *request*, so a five-thousand-segment stream whose server stalls each request just under it is bounded by nothing.
- **A `206` is only trusted if its `Content-Range` starts where the request asked**, and its body is length-bounded either way: a 206 that runs past the range it promised is the same corruption as a 200 nobody sliced.
