# Background Jobs and download compatibility

The Job Service is the durable control plane for user- and operator-facing background work. It accepts a Job before execution, stores lifecycle, ownership, replay input, claims, capacity, events, outputs, and lineage, and fences executor writes with an execution token. Downloads, exports, imports, Resource Reduction computation, maintenance, plugin actions, plugin command runs and imports, and schedules use this shared plane with their specialized executors. `job-summary-export@1` is a durable owner-visible Kind whose filtered queries use the same visibility predicate as interactive summary. Its sealed filter is decoded with plain JSON, so a worker from an older release silently drops a filter field it does not know (the inbound relationships) and fails on a token it does not know (`state=partial`); dimensions added after v1 are therefore refused for exports in `unsealableSummaryFilterDimension` rather than sealed, and the interactive summary keeps them. The external Job Center API and UI are enabled; startup migration readiness checks and the registered Kind inventory guard the cutover.

`download_queue/` remains an in-memory executor and compatibility surface. Its entries can be evicted at `MaxQueueSize` or after their retention period, and they do not survive restart. A queue entry is not the durable Job record. `DownloadHistoryEntry` remains for the legacy `/downloads` history and related compatibility behavior; the Job tables are authoritative for canonical lifecycle and immutable execution identity.

- **Acceptance and outcomes:** a canonical download Job is accepted before the transfer starts. The queue's `HistoryRecorder` still writes the legacy terminal history projection. A failure in that legacy write does not replace the canonical Job outcome.
- **Retry identity:** Retry of canonical work creates a new Job with a `retry-of` link and leaves the source Job's outcome unchanged. The legacy handle follows the current Retry leaf, while a canonical UUID always names one Job. An old history entry without a canonical Job reference may use the legacy resubmission path.
- **Compatibility reads and controls:** existing download, job, history, and SSE routes continue to expose their established legacy representations. A compatibility handle resolves to the current Job for get/list/events/control. Canonical SSE uses `version=2` and its own cursor/identity format. Keep these projections aligned with the Job Service when changing legacy routes. Every event stream reads through `currentJobEventsContext` (`server/request_scope.go`), which resolves the connection's cookie or token again on each read: the canonical stream per poll, the legacy streams through one `emit` closure that every frame, the initial state included, is written by: it makes the frame's projection reads, then takes the check (dated by the moment its credential read began), renders the frame, and writes it on that check or, if the check is older than `jobEventsCheckInterval` by then, on a new one taken after the render, projecting again when a check finds the account changed (when validation itself takes longer than the interval, the newest check is the bound) (events within that interval of the last check are held and emitted together, so a burst costs one read per interval); plus a one-second idle tick. `download_events_emit_test.go` fails if anything in the handler writes to the stream outside `emit`. It keeps the bound context while the resolved access is unchanged, because rebinding a group-limited account materializes its whole subtree. A stream bound once at connect keeps its old access after logout, disable or demotion, because SSE outlives the auth middleware.
- **Scope and authority:** ownership grants visibility; it does not grant permanent permission to repeat work. A Retry or redispatch validates current actor role, plugin access where relevant, and download target scope before running.
- **Retention:** Job history, replay input, and artifacts follow their Job-specific policies. The queue's in-memory cleanup and the legacy download-history retention are separate compatibility cleanup mechanisms; neither defines canonical Job retention.
- **Duplicate transfers:** the queue still prevents duplicate active URLs within its process. A dispatch that finds its URL already downloading, or a submission admitted with a claim that finds the same (`submitRemoteDownload`), hands its Job back to the queue (phase `waiting`, `requeueDownloadExecution`) and the adapter names it in `ClaimExclusions`, so the dispatch loop passes over it until the URL frees; it holds no claim and no capacity while it waits, because a waiting claim starves every other Kind, and it is never blocked, because nothing would release the block. The check and the start are one step under the registry write lock (`SubmissionOptions.ExclusiveURL`, `ResumeExclusive`). A paused entry holds no URL: it fetches nothing and may wait for a person indefinitely, so resuming it is what is arbitrated, the legacy resume route included. Every busy-URL question goes through one predicate, `activeEntryForURLLocked`, comparing `TransferKey`s; `ActiveDownloadForURL`, which the legacy retry routes and legacy deferred rows ask, delegates to it, so no two paths can disagree about whether a URL is busy. The Job claim and capacity budgets govern admitted execution across processes; a queue-local URL check is not a deployment-wide lock.
- **Shutdown is not an outcome:** `DownloadManager.Shutdown` records on each running attempt that the shutdown, not a person, stopped it (`claimShutdownStop`). The record names the attempt (its runID): an older attempt a pause stopped and a resume replaced can still be unwinding, and it must not hand back the attempt that replaced it. Every write an attempt makes about its Job while it runs (the hand-back, progress) publishes under the execution read together with that attempt's ownership check (`canonicalForRun`, `mirrorForRun`); its outcome is published after the stamp the same check fences. A download a durable Job owns goes back to the queue under its execution token with the reason `server-shutdown` and records no history row and no terminal job event; a held one stays held. Only a download no Job owns is stamped, as failed. Never route a shutdown through `job.Cancel()`: that is a person's cancel.
- **Failure codes are decided in the queue, classes in the adapter:** the queue codes a failed attempt from the error value (`download_queue.failureCode`) because past it a failure is text, and `downloadFailureKinds` maps each code to its class and to whether a Retry could answer differently. Retry is withheld only where the stored input can never be valid by itself (`invalid-url`); anything that depends on the remote, the library or policy (a 4xx, an unsupported stream, an existing resource, a refused address) keeps it. `Commands` and `SelectCommandJobs` read the same table, so the Retry filter and each Job's advertisement cannot drift. An error that knows its own cause implements `download_queue.CodedFailure`.

**Job progress metrics and graphs.** A progress tick is a snapshot on the Job row, never a Job Event, and it never moves the Job's version. Beside the primary measure it carries up to 8 metrics (`models/jobmetrics`, a leaf under `models/` so that `plugin_system` and `plugin_commands` can validate a metric without importing `jobs`), 3 of them graphable. `jobs.advanceSeries` keeps a bounded progress series on the row: one point per interval, compacted by merging pairs and doubling the interval at 120 points, first point kept. Speed, ETA and a stopped Job's average are derived in Go (`Snapshot.LiveRate`, `ExpectedFinish`, `AverageRate`, the last over banked running time, not the series' span) so the API, the SSE frame and the `/jobs` template agree, and every surface formats them alike: `jobStatsText` in `src/components/jobCenter.js` and `jobRowStats` in `job_progress_format.go` follow one case table (`template_context_providers/testdata/job_progress_format.json`) that both test suites read. A Job changes its unit only at the cost of its history (`advanceSeries` drops the old unit's counts), so an executor reports one measure to the end: an HLS download counts segments through the assembly, with the bytes as a metric. Live delivery is a `job-progress` frame on the canonical stream after `job-caught-up`, read through `Service.LiveProgress` under the same visibility predicate as events. Like an ordinary `job-caught-up` it **has no SSE id**: giving it one would move the durable delivery cursor. (Two `job-caught-up`s carry an id, both where the stream chose the cursor rather than resuming the reader's. A reset's, sent when a resume cursor is above the highest sequence this database has issued, `JobEventSequence.Value`; moving the cursor to the viewer's head is its purpose. The test is the allocator, never the viewer's visible head, because retention and narrowed access leave issued cursors above that head, and the Jobs panel answers a reset by stopping with a Reload page button while the Job Center and detail pages reload. And one after `start=head` with no cursor, which starts at the allocator's head so a page that reads its Jobs itself is sent no history; its id is what the browser's own reconnect resumes from.) Its timestamps are not a cursor either — each process writes its own clock — so each poll reads a 30 s window and dedupes per connection by the snapshot last sent. Plugins report through the table form of `mah.job_progress` (a report the 200 ms throttle held back is flushed at settlement) and command runs through `::mah-progress` stdout lines, which are stripped from the output tail and redacted with the run's secrets. The command mirror writes through `Service.UpdateProgress` with a fresh handle, not through the claimed `jobs.Execution`: `claimPluginCommandJob` claims inside a transaction, and an Execution carries the handle it was claimed with.

**Job rollout and operator invariants:**

- `JOB_REPLAY_KEY` is a comma-separated keyring of base64-encoded 32-byte keys. The first key seals new inputs; later keys only decrypt old envelopes. Keep the same stable keyring on every PostgreSQL writer. Persistent SQLite's generated `_job_replay_key` is mode `0600`; include it with the database backup. Keep an old decrypt key until all envelopes using it expire or are explicitly forgotten.
- `JobWriterEpoch` is checked before migrations, cleanup, plugin activation, or dispatch. Deploy the epoch-aware release everywhere and drain older writers before the minimum epoch advances. An older binary must refuse an advanced database; rollback uses a compatible canonical reader, never a plaintext writer.
- Legacy download and Job handles/routes remain supported for at least one documented release and six months after canonical cutover. A legacy handle may follow its Retry leaf; a canonical UUID always identifies one immutable Job.
- A backup from before plaintext retirement must pass the current backfill and retirement verification barrier after restore, using the matching files and replay key, before traffic or older writers are allowed.
- Before admitting traffic after rollout or restore, an administrator must check `GET /v1/admin/jobs/migration-readiness`: require `ready: true`, inspect `writerEpoch` and `phase`, resolve every entry in `blockers`, and review every Job in `reviewCandidates`: unfinished Jobs with no recorded principal, owner, actor or deletion mark, which run as the host and may be the work of an account deleted before deletion marks existed. They are listed rather than blocking, because readiness gates startup and the row cannot tell them from legitimate actorless work. A prior completion marker does not establish readiness for a restored database.
- Retention deletes ended Jobs and keeps the source mappings that name them, so a retired source routinely outlives its Job. Readiness therefore counts a mapping whose Job no longer exists as needing no replay (`migrationJobReplayReady`). That is sound only while retention is the one thing that deletes Jobs and never deletes a nonterminal one (`TestRetentionNeverPrunesANonterminalJobWhateverItsDeadline`); anything new that deletes a Job must keep both true.
- Plugin command runs and command imports require one fenced command-runtime owner per database and staging namespace. Other Job Kinds and the Job Service can run on multiple processes; independent command runtimes with separate staging roots cannot share one database.
