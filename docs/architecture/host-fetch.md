# Host fetch User-Agent and per-download headers

Every fetch the host makes on a user's behalf went out as `Go-http-client/1.1`, which at least one supported platform's media endpoint answers with 403. `hostfetch/` is a leaf package, in the shape `hls/` established, holding the browser-like default, the intake validation and one `http.RoundTripper` decorator.

- **One choke point, not one edit per request site.** The clients are already built per call and already carry the caller's egress policy, so the decoration composes with `ApplyEgressPolicy` and covers the initial GET, every HLS playlist, key, rendition and segment, and every redirect hop — with one implementation rather than three. `mah.http` is deliberately untouched: that is a plugin fetching under its own honest agent, not the host downloading for a person.
- **The User-Agent goes everywhere; a caller's own headers go to the submitted URL's host only.** A `User-Agent` *among* those headers is therefore lifted out and becomes the download's agent on every host: an endpoint that refuses one agent refuses it on its CDN too, so binding it to the submitted host would fix the playlist and leave every segment failing — and it names the fetcher rather than the user, which is the same reason the deployment's own is safe anywhere. An empty value anywhere means the default, never an empty header line. A reviewer put the counter — a caller could encode a secret in it, and it then reaches a host the playlist chose — and that is the accepted cost: the User-Agent is the one header whose purpose is to be announced to every server a transfer touches, the deployment's own already is, and the header map bound to the submitted origin is where a value that must not travel belongs.
- **The bind is to the *origin*, not the host.** Scheme and effective port are both part of it: a redirect from `https` to the same name over plain `http` is a downgrade, and matching on the host alone put a `Cookie` on the wire in clear.
- **Map headers are `Set`, not filled-if-empty.** net/http writes its own `Referer` on every redirect, which a fill-if-empty rule mistook for a header the calling code owned — so a caller's `Referer`, the single most likely reason to use this at all, survived the first request and was replaced on every hop after it. Nothing else collides: `hls` sets only `Range`, and `Range` is refused at intake. The *User-Agent* keeps the fill-if-empty rule, because there the calling code's own value is the more specific one.
- **`SubmitForPlugin` copies the map it validated.** `SubmitMultiple` gives every job a shallow copy of one creator, so all of them would otherwise share a map the submitter still holds — one that can change after the validation that approved it, while a worker iterates it and the history row is serialized from it. The agent identifies the fetcher and says nothing about the person who asked, so no host is unsafe. A playlist, by contrast, names further URLs and the host policy permits every public host, so replaying a `Cookie` or an `Authorization` onto whatever a playlist says is a credential handed to a server the *content* chose. The same rule makes the decoration redirect-safe for free: net/http strips `Cookie` and `Authorization` across a domain change, and a decorator re-adding them per attempt would silently undo that. The comparison is **host:port**, not hostname — two httptest servers differ only by port, so a hostname rule passes a cross-host test while sending the header anyway. A header the calling code already set wins, because `hls` sets its own `Range`.
- **Every URL of a newline batch is decorated separately.** `AddRemoteResource` fetches each line, and each line is a URL the caller submitted with these headers, so all of them receive them — but each binds to its *own* host, which is what keeps them off the hosts a playlist beneath any of them goes on to name.
- **Refused at intake, not at request time.** Connection-level and framing headers (`Host`, `Content-Length`, `Connection`, `Keep-Alive`, `Transfer-Encoding`, `Upgrade`, `TE`, `Trailer`, and the whole `Proxy-*` family by prefix rather than by the three names anyone thinks to list) are net/http's to own, and `Range` is `hls`'s — a caller-supplied one misassembles the media silently and breaks the playlist sniff. `SubmitForPlugin` is the single door every queue submission passes through (the API handler, the plugin submitter, `SubmitMultiple`, a retry), and `AddRemoteResource` checks before it fetches anything. By the time a worker builds a request the submitter is gone and the only surface left is a failed history row.
- **The headers live on `ResourceFromRemoteCreator`,** which is what persists them on the download history payload and replays them on retry — a download that only worked with a `Referer` must still work when it is retried on another worker months later. It also means a `Cookie` is stored in the database until the row is swept; the payload is never rendered to a page. They are `schema:"-"`: gorilla/schema decodes no map, so this is a JSON-body option and the create-resource form carries none.
- **The plugin option is one helper read by both surfaces** (`applyRemoteHeaders`), so an author writes one shape of options whether they call `mah.db.create_resource_from_url` or `mah.download.submit`. No new capability: a header widens no egress, the transfer is policed exactly as before, and `mah.http` already sends arbitrary headers to allowlisted hosts.
- **The setting is runtime-editable** (`remote_user_agent`), because a 403 from one platform is a thing to fix without a restart. Empty anywhere means "not configured" and selects the default; it never means "send no User-Agent", which is the value that produced the 403.
