# Authentication & roles

Auth is **opt-in**. With `-auth` set, requests must authenticate via a browser session cookie (login at `/login`) or a per-user API token (`Authorization: Bearer <token>`, used by the `mr` CLI). Four roles:

- **admin** — full access, including system settings, plugin management, categories, and user administration (`/admin/users`, and `/admin/users/edit?id=N` for changing a role, scope, disabled state or password without deleting the account). Both paths must stay listed in `isSystemPath` (`server/authz_policy.go`), which matches template paths exactly — a new admin page omitted from it falls through to `capRead` and becomes readable by every authenticated role. An `isEditorPath` entry does not gate a GET page either, because that branch downgrades safe methods to `capRead`; the shares dashboard (`/admin/shares`, which lists every shared note with its public token) is therefore gated at `capEditor` for every method by an explicit `requiredCapability` case, and `TestNoAdminTemplatePageIsCapRead` fails the build if any `/admin/` template page resolves to `capRead`.
- **editor** — CRUD on entities, except creating/editing Categories and Resource Categories, and no system settings.
- **user** — CRUD on resources and notes (plus subgroups, tagging, note sharing, group import/export, and plugin-action execution); optionally confined to a single Group's subtree.
- **guest** — read-only, always confined to a single Group's subtree.

Group-limited users/guests are confined to their scope group and all of its descendants across lists, single-item reads, search, MRQL, file serving, group export, writes, and the public share server (fail-closed). Bootstrap the first admin with `-create-admin-user`/`-create-admin-password`. The `mr` CLI authenticates with `mr auth login` (stores an API token) or the `MR_TOKEN` env var.

**The share server resolves block references as the account that shared the note** (issue #89). It runs on the principal-less singleton, and four block kinds carry IDs it dereferences: gallery `resourceIds`, references `groupIds`, a table's `queryId`, and a calendar's `source.resourceId`. Unchecked, a group-limited user wrote outside IDs into a note of its own subtree, shared it, and read resource names and bytes, group descriptions, ICS events and saved-SQL output from the unauthenticated share port. Three layers close it. (1) `CreateBlock` and `UpdateBlockContent` refuse, for a scoped principal, a reference the scoped handle cannot see (`checkBlockReferencesInScope`, `ErrBlockReferenceOutOfScope`; invisible and nonexistent answer alike, so it is no existence oracle), and refuse a `queryId` table outright, matching `RunReadOnlyQuery`'s deny. (2) `ShareNote` re-checks every block of the note for a scoped caller before minting a token, which covers blocks written before the check or by another account; `POST /v1/note/share` answers that refusal with 403. (3) `ShareNote` records `Note.ShareCreatedByUserId`, and every share-server lookup that follows a block reference (page render, `/s/<token>/resource/<hash>`, calendar events, saved-SQL tables) runs on `ShareReaderFor(note)`: the context bound to that account as `principalForPluginActor` resolves it now, so a scoped sharer resolves only its subtree, a deleted or disabled one binds deny-all, and a saved-SQL table runs only when the sharer is unscoped. Layer 3 is what holds; layers 1 and 2 give the refusal a reason, and because 3 re-resolves at read time they take no row lock (a resource moved out of the subtree after the check simply stops resolving). The note itself is still found unscoped by its token, which is the authority to see it. Two cases keep the old, unscoped resolution deliberately: auth off (every caller is the implicit admin), and a share with **no recorded sharer** — minted before the column existed or by a principal-less caller — because nobody can say whose scope it should carry and binding deny-all would empty every existing share on upgrade; unsharing and resharing records the sharer. User deletion does **not** null the column (unlike the `CreatedByUserId` sweep): a NULL sharer means "legacy, unscoped", so nulling would escalate a deleted scoped user's shares, whereas a dangling id resolves deny-all and IDs are never reused (`AUTOINCREMENT` on SQLite, a sequence on Postgres). Layers 1 and 2 must read references exactly as the share server does, so all three, and the in-app table query handler, go through `block_types.ExtractBlockReferences` (exact keys, like the share template, the browser and `block_ref_cleanup`). An earlier private struct decode matched keys case-insensitively with the last one winning, so `{"resourceIds":[outside],"RESOURCEIDS":[]}` checked as empty and rendered the outside resource under an admin or legacy sharer. Calendar sources are read the same way: `block_types.ReadCalendarSources` reads `calendars[].source.{type,url,resourceId}` by exact key for `ValidateContent`, `ExtractBlockReferences` and `GetCalendarEvents` alike. A struct decode there was not enough even with both sides using it, because which duplicate wins depends on key order and the stored bytes do not keep it: the `block_ref_cleanup` scrubs re-marshal through a map (keys sorted bytewise) and Postgres jsonb reorders keys on write, so `{"type":"resource","resourceId":outside,"Type":"url",...}` checked as a URL source and, after the scoped user deleted one of its own resources, fetched the outside ICS file. With exact-key readers a re-marshal cannot change what is read, so the scrubs need not preserve key order. As defence in depth, the gallery, references, table and calendar `ValidateContent` refuse content holding two keys that encoding/json would match to one field (`RejectAmbiguousBlockKeys`, `ErrAmbiguousBlockContent`), folding as encoding/json does (Unicode simple folding: `"Calendarſ"` with U+017F matches `calendars`, U+212A Kelvin sign matches `k`), and the scope check refuses such stored content at share time. Calendar content is checked at every level, since its readers consult nested objects and it has no user-chosen keys; the other types only at the top level, which is all their readers consult, because table rows are keyed by column ids that may legitimately differ only in case. Write-time refusals map to 403 on `POST /v1/note/block` and `PUT /v1/note/block`. Pinned by `server/api_tests/share_scoped_block_refs_test.go` and `share_scoped_calendar_keys_test.go`.

**Saved SQL Queries** are arbitrary SQL, and editors keep authoring them (`POST /v1/query` is `capEditor`); every unscoped principal can run one (`/v1/query/run` is read-via-POST, `capRead`). What keeps that inside the role model is the handle they run on, not the route. On SQLite `models.CreateReadOnlyDatabaseConnection` opens it with its own driver, `models.ReadOnlySQLiteDriverName`, whose ConnectHook sets `PRAGMA query_only = ON` and `SQLITE_LIMIT_ATTACHED = 0` and installs an allow-list authorizer: SELECT, column reads, function calls and recursive CTEs pass, and so does `PRAGMA data_version` in its read form only (no value), because FTS5 issues `PRAGMA main.data_version` from inside every MATCH and without it every saved query over an `*_fts` table fails at row iteration; every other PRAGMA, and every write, DDL, ATTACH/DETACH and transaction statement is denied, so `query_only` cannot be switched off again; and a column read is allowed only from a table `models.IsSavedSQLAllowedTable` allows. That is an **allow-list shared by both databases** (`models/saved_sql_tables.go`): every table the server migrates is classified there as readable (entities, their join tables, and on SQLite their `<table>_fts*` full-text index and FTS5 shadow tables) or not (credentials and sessions, runtime settings, the audit log, per-account data, owner-restricted Reductions, template history, every plugin and Job table, downloads). `TestSavedSQLTablesClassifyEveryMigratedTable` (main package, and its Postgres twin under the `postgres` tag) migrates exactly what a server start migrates (`migrateModels`, `migrateJobCore`, FTS setup) and fails on a table the list does not decide and on a list entry naming no table, so a new table is unreadable until someone classifies it. Views are refused even over allowed tables (the server creates none), as is the SQLite catalogue (`sqlite_master`/`sqlite_schema`). One read the allow-list cannot judge by name: SQLite reports a FROM item none of whose columns are read (`SELECT count(*) FROM x`) as a READ with an empty column and the FROM clause's own name, which for a CTE is the CTE's name, so `WITH RECURSIVE c(x) ... SELECT count(*) FROM c` arrives as table `c`. The authorizer lets that empty-column reference through unless the name is a classified-denied table or `sqlite_*`; a real table behind it is still refused by the bytecode check below. **The authorizer is not the only gate, because SQLite does not report every read to it**: the columns a `USING` or `NATURAL` join merges are read from the right-hand table with no `SQLITE_READ` (SQLite 3.53), and once any column of a table is read the empty-column READ is skipped too, so `SELECT password_hash FROM (SELECT 1 AS password_hash WHERE 0) FULL JOIN users USING (password_hash)` dumped every hash with the authorizer never hearing of `users` (also on master since #144). So each connection of the driver is wrapped (`savedSQLConn`, `models/saved_sql_bytecode.go`): it implements neither `QueryerContext` nor `ExecerContext`, so database/sql prepares every statement through it and runs only the first statement (text after it other than comments and semicolons is refused); after go-sqlite3 prepares the statement, the wrapper compiles `EXPLAIN <query>` on the same connection and refuses the statement unless every `OpenRead`/`ReopenIdx` targets, in the main database (P3 = 0, no register-held root page), a root page that `sqlite_master` maps to an allowed table or an index of one. Root page 1 (`sqlite_master` itself) is in no map and so refused; write and schema opcodes are refused outright. The map is read through the same connection under an `internal` flag that opens the authorizer to exactly `BEGIN`/`ROLLBACK`, `PRAGMA schema_version` and `main.sqlite_master`, inside one read transaction together with the EXPLAIN (so the map and the bytecode describe the same schema), and cached per connection under `schema_version`, which every DDL bumps. Virtual-table cursors (`VOpen`) name no table and are not mapped: what a statement can reach that way is the FTS5 indexes, whose own reads of their shadow and content tables go through the authorizer column by column, json_each/json_tree, and pragma functions whose PRAGMA the authorizer refuses; the build has no `dbstat`, `sqlite_dbpage` or `sqlite_stmt`. CTE and subquery columns raise no READ at all (SQLite skips ephemeral tables). json_each/json_tree, fts5vocab and bm25/highlight/snippet raise no other authorizer action. Table-valued pragmas such as `pragma_table_info` stay denied. `mode=ro` in the DSN alone was not enough (GitHub #88): it protects only the main schema, so a database ATTACHed on the same connection opened read-write, and go-sqlite3 drops it silently without the `file:` prefix. The hardening applies whatever `DB_READONLY_DSN` says, including when it is unset (an empty private temporary database). On Postgres `RunReadOnlyQuery` runs the text as one prepared statement (the extended protocol refuses a second statement) inside a `READ ONLY` transaction that has already taken its snapshot (so `SET TRANSACTION READ WRITE` is refused); which tables it can read is the role's, so **the server verifies the role** (`models.VerifyPostgresReadOnlyRole`, through the read-only handle itself) and refuses it when it is the main `DB_DSN` role or a member of it, a member of any other non-predefined role (it could `SET ROLE` to it), a superuser, `BYPASSRLS`, a member of `pg_read_server_files`, `pg_write_server_files`, `pg_execute_server_program`, `pg_read_all_data`, `pg_write_all_data`, `pg_monitor`, `pg_read_all_stats`, `pg_read_all_settings`, `pg_stat_scan_tables`, `pg_signal_backend`, `pg_maintain`, `pg_checkpoint`, `pg_create_subscription` or `pg_use_reserved_connections` (those a server version lacks never appear among its memberships), connected to another database than the main connection, holding `CREATE` on any schema, holding INSERT/UPDATE/DELETE/TRUNCATE/REFERENCES/TRIGGER (table- or column-level) on any relation or any privilege on a sequence, or able to `SELECT` any column (`has_any_column_privilege`, which sees column grants and grants to `PUBLIC` that `has_table_privilege` misses) of a table, view, materialized view or foreign table outside the allow-list in schema `public`. Every failed check is named in the error and the log. The verdict is cached for a minute (`savedSQLRoleCheck`, shared by pointer across context copies; the check runs outside the lock, and a verdict is stored only if its check started after the stored one's, so a slow stale pass cannot overwrite a newer fail) and taken fresh at startup after migration (`CheckSavedSQLRole`), so a later `GRANT` reopens nothing for longer than that. **With `-auth`**, while the role fails, `RunReadOnlyQuery`, `RunReadOnlyQueryByName` and `GetDatabaseSchema` return `ErrSavedSQLUnavailable` wrapping the failure → **503** (the request is well formed and the caller may make it; the deployment's configuration is what is missing, and the refusal lifts by itself once the role is fixed — not 403, which is about who asks, nor 409, since no resource's state conflicts). The scope check runs first, so a group-limited principal still gets 403. **With auth off** every request is the implicit administrator, who can read those tables anyway, so a failing role only logs a warning and shows the `/queries` banner; saved SQL keeps running. An unset `DB_READONLY_DSN` on Postgres is not special-cased: lib/pq then connects by `PG*` defaults, and the check judges whatever role that reaches (the main role fails it). `mahresources -print-readonly-role-sql=<role>` prints the script (`models.PostgresReadOnlyRoleSQL`, run as a superuser: `CREATE ROLE` and the `ALTER ROLE` attributes need one) that creates a role the check accepts: `LOGIN` with no other attribute, everything revoked in `public`, `USAGE` on the schema and `SELECT` on each allowed table; no `ALTER DEFAULT PRIVILEGES`, since a new table getting no grant is the point. It is a server flag rather than an `mr` command because `mr` talks to a running server over HTTP, while this is an offline setup step like `-create-admin-user`, and the allow-list it prints lives in `models`. `IsReadOnlyDBEnforced` reports what the code installed or verified (the SQLite driver name; on Postgres, the role check), never a substring of the DSN; it and `ReadOnlyDBProblem` drive the warning banner on `/queries`. `GET /v1/query/schema` lists only allowed tables and, like running saved SQL, is refused to group-limited principals (`ErrSavedSQLScoped` → 403). **Trust model:** an editor's SQL, and an unscoped user running it, can read every row of the content tables regardless of group subtree, and nothing else; that holds on SQLite by construction and on Postgres only while the role check passes, which under `-auth` is a precondition for running at all. Tests: `models/saved_sql_driver_test.go`, `application_context/saved_sql_readonly_test.go`, `server/api_tests/saved_sql_hardening_test.go`, `server/api_tests/saved_sql_fts_test.go` (fts5 tag), `main_saved_sql_tables_test.go`, and under the Postgres tag `main_saved_sql_tables_pg_test.go`, `saved_sql_readonly_pg_test.go` and `saved_sql_role_pg_test.go` (the generated script's role passes and is refused the sensitive tables; each failing privilege is named; a role with `SELECT` on `users` gets 503 under `-auth` and only a warning without it).

**List filters are confined twice.** The scope callback confines the rows a list *returns*; it never sees the rows a filter's subqueries *read*, because those are raw SQL text or carry a table alias (`groups p`, `notes n`) that `scopeColumn` does not map. So the legacy list-filter builders in `models/database_scopes` take a required `database_scopes.Visibility`, built by `ctx.listVisibility()` from `principalForcedScope` (scope root, deny-all, or unconfined), never from the request-decoded query DTO. It is the legacy counterpart of MRQL's `TranslateOptions.VisibleRootID`, and the rule is the same: a row reached through a filter behaves as if it did not exist. In `GroupQuery`, the parent branches (`SearchParentsForName`, `SearchParentsForTags`, `parent.*` MetaQuery) skip the scope root, because its parent is the only parent outside the subtree; the child branches need no guard, since the subtree is closed downward. The id-list filters (`Groups`, `Notes`, `Resources`) count a named group, note or resource only when it is visible, so naming a hidden one reads the same as naming a missing one and the AND-count yields nothing. `ResourceQuery` and `NoteQuery` follow the same rule for their `Groups` and `Notes` filters; `ResourceQuery.ShowWithSimilar` counts only a duplicate image hash whose resource the caller can see (as MRQL's `similarImages` does). `OwnerId` with `IncludeSubgroups` requires the named root to be visible: a hidden ancestor's subtree holds the caller's whole subtree, so without the guard it would list the caller's rows where any other hidden or missing id lists none, an oracle for the scope root's hidden ancestry (`TestResources_OwnerSubtree_ScopedToSubtree` pins that a hidden ancestor answers like a missing group). `RelationTypeQuery`'s `ForFromGroup`/`ForToGroup` resolve a hidden group to no category, so an invisible group answers like a missing one; `GET /v1/relationTypes` is served through `scopedAPI` so the principal reaches it at all. Every predicate binds no parameters (the root is a `uint` formatted into a recursive subtree CTE), so it costs nothing against the parameter ceilings the allow-list already presses on (see `visibleGroupIDs`). The CTE reads the live tree while the callback uses the request-start allow-list snapshot; a re-parent during one request can briefly make the two disagree, the same trade-off MRQL makes.

**The allow-list is a snapshot, and writes that change containment re-derive it.** `applyPrincipalScope` resolves a group-limited principal's subtree once, when the request context is bound, which is before the request body is read; a body may take up to the server's `ReadTimeout` to arrive. Writes that move something between subtrees decide future visibility, so a stale "this group is mine" could undo an admin's move of that group out of the subtree. They therefore re-derive the allow-list on their own transaction with `rescopeTx`, after their tree lock where they take one, and run every scoped statement after it against the current tree: `UpdateGroup` (which also refuses a target that has left the subtree explicitly, since its id-keyed tag and relation writes would otherwise still run, and whose owner-clear branch now takes the tree lock like a re-parent), the mass edit (every op, for a scoped caller), `MergeGroups`, `EditResource` when it sets the owner, and `CreateOrUpdateNote` (create and update, because every note write sets the owner). The fresh subtree is rooted at the request-bound `ScopeGroupID`, so `rescopeTx` first re-reads the account on the same transaction (`accountStillBound`) and refuses the write (`gorm.ErrRecordNotFound`) when the account is gone, disabled, or no longer has the role and scope group the principal was built from; otherwise an admin narrowing the user's scope from S to A mid-request would leave the write judged against subtree(S). The re-read runs for every account-backed principal, not only a group-limited one, and these writers call `rescopeTx` whatever the caller's role: a request bound while the account was unscoped (a user, an editor or an admin) carries no filter at all, so an admin confining that account mid-request would otherwise let the parked write pull any group into its new scope. Only the no-auth root principal (`SuperUser`) and a principal with no account skip it. That read takes no row lock: on SQLite the transaction already holds the writer lock, and on Postgres a `FOR SHARE` would invert the groups-before-users order `UpdateUser` follows and deadlock against the re-parent's foreign-key check on the newly assigned scope group, so an account change still uncommitted at that instant is not seen. A disabled or demoted account's other, non-containment writes in a parked request still run on the stale principal. Resource and note owner changes take no tree lock, so on Postgres they are not serialized against an admin move that has not yet committed. Every other read and write still uses the snapshot; that is the read TOCTOU accepted in `docs/todo.md`, and it includes renaming or tagging a group, creating a subgroup in it or uploading a resource into it through a request bound before the group was moved out. Re-binding the scope after the body is read was deliberately not done: it narrows the window but does not close it.

**Share tokens are disclosed only to principals that may share** (`CanWrite`, the capability `POST /v1/note/share` demands). A token is a bearer credential for the unscoped share server, which lets its holder write todo state and outlives the account that read it, so `Note.ShareToken` is `json:"-"` and no generic encoding of a note carries it, nested ones included. `AfterFind` sets the non-secret `HasShare` instead. The only read disclosures are `GET /v1/note` (a writer-only wrapper in `GetNoteHandler`), the note page's sharing panel (`NoteContextProvider` hands a read-only caller a copy without the token, and `noteShare.tpl` renders only the badge for it), and the editor-only `/admin/shares` (#107). Templates are the other way out: the built-in `[property]` and `[conditional field=]` read Go fields by reflection, which `json:"-"` does not stop, and a note type's templates render on many pages (cards on groups, resources, tags and note types, the hover card, MRQL `renderedHTML`, deferred `[lazy]` bodies, rendered text blocks) against the note as loaded. So the shortcode resolver withholds credential fields (`ShareToken`, `TokenHash`, `CsrfToken`, `PasswordHash`) unless the render context is marked `shortcodes.WithCredentialFieldsVisible`, which `withAuthentication` sets from `CanWrite` on every request. An unmarked render fails closed; the share server marks its own, whose visitor already holds the token.

Group-limited principals are denied every **plugin-code endpoint** (`/v1/plugins/...`, `/plugins/...` — the JSON API catch-all, block/display render, and plugin pages) **unless an operator has opened that specific plugin to them**. The deny is fail-closed in `withAuthorization` and is now per plugin: `pluginCodePathName` reads the name out of the path, and a path whose name cannot be read (`/v1/plugins/manage`) is refused, because "which plugin is this?" has no answer that could be allowed. Unscoped roles (admin/editor/unscoped user) are unaffected. **One plugin-code route names no plugin:** the batch block render, `POST /v1/plugins/block/render-batch`, renders whichever plugin each block's type names, so its `block` is a route word. The middleware once read it as a plugin called `block`, which refused every opened plugin's blocks to limited accounts and would have opened all of them once a plugin of that name was opened. `withAuthorization` now skips that exact path and method (never a prefix, and not the `.json` or `GET` variants, which reach the JSON API catch-all and stay gated as "block"), and `GetPluginBlockBatchRenderHandler` gates each block with `auth.PluginAccessFor`, answering a refused block with the same `plugin block not found` a missing block gets. `block` and `manage` are reserved plugin names (`reservedPluginNames` in `plugin_system/manager.go`), so a plugin carrying one fails discovery with a clear error. A future multi-plugin route under `/v1/plugins/` or `/plugins/` needs the same treatment. Both render POSTs, the batch route and `POST /v1/plugins/{name}/display/render`, are `capRead` in `requiredCapability` (`isPluginRenderPost`, matched on the raw path), matching `GET .../block/render`, so a guest renders an opened plugin's blocks and metadata displays. They are deliberately not in `isReadViaPost`, because `csrfExempt` reuses that list and render Lua can still reach `mah.db` writers, so a cookie-authenticated render POST still needs its CSRF token.

The toggle also governs **plugin actions** for a group-limited caller (`/v1/jobs/action/run` → 403), which is a deliberate narrowing of what those accounts could do before: an action is the most direct way to make a plugin's Lua run, and gating the indirect surfaces while leaving it open would make the setting mean something other than what it says. Unscoped roles are unaffected, so a deployment with no scoped users sees no change. **What is offered follows what is allowed**, through one predicate and no second copy of it, which is the doctrine `DownloadHistoryQuery` already carries: a listing and the mutation it leads to drift apart the moment they are written twice. That predicate is `auth.PluginActionAccessFor`, and it answers at three places: the run path refuses with it (`actionPluginAccess`), `GET /v1/plugin/actions` filters with it, and `wrapContextWithPlugins` filters the six action lists the pages actually render (`offeredActions`), which is the detail sidebar, the card menu and the bulk bar. It is `auth.PluginAccessFor` narrowed by the capability an action run demands: `requiredCapability` classifies `POST /v1/jobs/action/run` as `capWrite`, and `principalSatisfies` answers `capWrite` with `Principal.CanWrite`, which is the method it calls. **A guest is therefore offered no action at all**, whatever the toggle says, because that refusal is `withAuthorization`'s and is made above the handlers, where a filter built on reach alone cannot see it. The narrowing is deliberately not folded into `PluginAccessFor`: the surfaces that one gates (pages, shortcodes, slots) are `capRead`, and a guest keeps them once an operator opens the plugin. The classification is the one half of the rule that exists twice, because `server/api_handlers` cannot import `server`, so `TestActionRunRequiresTheWriteCapability` pins it. That is where a user meets an action, since **nothing in the browser calls the listing endpoint**; fixing only the endpoint would have left every visible button in place. This is a dead control removed, not a boundary moved: drawing a button and listing an action both run no plugin code, and the 403 is what holds. One case diverges, a request with **no principal**, which is unrestricted at the two handlers and refused at the render seams. That is `actionScopeRestricted`'s existing treatment of a missing principal, and refusing the plugin while granting every entity would answer "who is asking?" two ways in one handler. It costs a deployment nothing: `withAuthentication` attaches a principal to every non-public path in either auth mode, and neither of these is public, so the only callers reaching it are `server/api_tests`'s bare handler mounts, pinned by `TestActionHandlers_BareMountsAreTestsOnly`. The operator's decision has a CLI surface, `mr plugin scoped-access <name> --allowed=true|false`, whose `--allowed` is required rather than defaulted so a bare invocation cannot read as a silent revocation. **Listings follow reach too.** The nav menu items (`offeredMenuItems`, in `wrapContextWithPlugins` and the error-page enricher), `GET /v1/shortcodes/docs` and the shortcode lint/preview catalogue (`offeredShortcodeDocs`) are filtered with `auth.PluginAccessFor`, the reach predicate rather than the action one, because a page and a shortcode are reads a guest may use once the plugin is opened; the lint catalogue is filtered as well because a verdict on `[plugin:x:y]` would otherwise confirm that a closed plugin exists. The "Manage Plugins" link is shown to admins only (it is `capSystem`), and the Plugins dropdown is omitted when nothing is left to show. Acknowledged open listings, like `/v1/plugin/displayTypes`: `GET /v1/note/block/types`, because the block editor needs the full list to render blocks a note already contains. **Hooks stay ungoverned** — they fire from ordinary writes, not from a plugin URL. The operator's decision lives on `PluginState.AllowScopedPrincipals` (off by default, `POST /v1/plugin/scopedAccess`, a button on `/plugins/manage`), and is deliberately **not** part of the consent record: `Grants` mirrors what the plugin asked for, and re-consent semantics must not turn on an operator's own decision about who may knock. It says nothing about what the plugin may then do — a confined caller's `mah.db` stays bound to that caller's subtree and role. `PluginAllowsScopedPrincipals` reads an atomic snapshot rather than the database, because the render seams ask once per plugin per request and six slots live in the base layout; it is invalidated on enable/disable and on the toggle, and a disabled plugin never reads as reachable. Two properties are load-bearing and were both defects first: the writer **invalidates rather than refreshes** (a refresh that failed would leave the pre-write snapshot serving "allowed" while the operator was told the write failed), and `scopedPluginAccess.publish` enforces the one rule that is decidable locally — a **generation counter** discards a load that began before an invalidation *this process* made. It deliberately does not try to order two concurrent loaders: that was attempted twice (by publish time, then by start time) and both are wrong, because no local clock says when the database was actually observed and a loader that starts first can observe last. What bounds an answer this process did not decide is the **TTL**, and that bound is only true because a snapshot is stamped with a time the database had certainly not yet been read (before the query, not after) and an already-expired answer is refused at publish — otherwise a stalled loader republishes a stale answer with a fresh clock, indefinitely. The publish lock deliberately spans no I/O: holding it across the database read inverts against the connection pool, and a caller inside a transaction holds the connection while the loader holds the lock — on SQLite, a deadlock, and transaction clones share this very cache. A 30s TTL bounds the staleness a second process cannot be told about.

The render seams gate **per plugin** through `auth.PluginAccess`, published on the page context as `_pluginAccess`. A refused shortcode renders the same neutral comment a context with no plugin renderer renders (`shortcodes.ErrPluginUnavailable`), so a page cannot be read for which plugins exist or which ones an account may use. Where a render path supplies no predicate, `pluginAccessFromContext` falls back to `auth.PluginAccessFor(reqCtx, nil)` — which is exactly the old whole-request rule — so an unenumerated path degrades to the previous behaviour instead of blanking plugins out for admins. `internal/arch/plugin_render_gate_test.go` counts either form.

**The deny matches URL paths, and hooks are not one.** They fire from ordinary scoped CRUD that a confined user is entitled to perform, so a plugin's Lua runs on a confined user's own write whatever that deny says — which is why `mah.db` is scoped to the *acting principal* rather than relying on the deny to keep confined callers out. `BindInvocation` resolves the actor id to the stored account (`principalForPluginActor`) and binds its real scope group; an actor whose account cannot be read — deleted or disabled since an async job or drained HTTP callback captured its id — is bound **deny-all for subtree-scoped data**, never unscoped. What binds is *scope*, and — since the role-capability guard — the acting **role** as well, at the operations that need one. `requireTaxonomyRole` and `requireEditorRole` (`application_context/role_capability.go`) refuse an operation whose capability the bound principal's role does not carry, returning `ErrRoleCapability`, which `statusCodeForError` maps to **403** by type rather than by wording. **A context with no principal is allowed**: startup seeds, the hash and thumbnail workers and the singleton handle carry no identity, and there is no caller there whose role could be asked. The guard sits on the *operations*, never on the tables, and that distinction is load-bearing: a plain user's remote upload find-or-creates a `Category` from `GroupCategoryName` (`resource_upload_context.go`), and group import creates and renames rows in six taxonomy tables — both legitimate at `capWrite`, and neither one goes through a guarded operation. The rows are `capWrite`; a Template Carrier's *payload* is not. Group import keeps a new Category's, Resource Category's or Note Type's templates, CSS, `MetaSchema`, `SectionConfig`, `MetadataIndexes`, `AutoDetectRules` and `ApplyTemplatesToShares` only when `requireTemplateCarrierEdit` allows the importing principal that carrier type (admin for the first two, editor for Note Types). Below that role it creates the row with its name, description and GUID only, before revision #1 is taken so the payload never reaches history, and adds a warning to the result. What it keeps passes `validateCarrierTemplates`, the save path's validation, or the apply fails. `groupio` cannot see the principal, so the facade passes the answer down as `groupio.Deps.Carriers` (`groupioCarriers`), read from the context the apply runs on: a queued apply the adapter dispatches as its stored actor is judged by that actor's role at apply time, while one submitted through `SubmitImportApply`, whose run closes over the request's context, is judged by the role at submission. A stripped carrier keeps its GUID, so a later import of the same archive by an admin reuses the bare row; its templates then come from the editor or from another carrier. Group Relation Types and Series carry no template payload and are still created at `capWrite` by import. **Every `mah.db` writer and `mah.db.transaction` requires `CanWrite` at `pluginDBAdapter`** (`requireWriteRole` as the first statement of each mutating method, and in `RunInTransaction` before the transaction opens), so a guest or the deny-all principal gets a read-only `mah.db` on any read surface (inject slot, shortcode, page, GET plugin API). The guard sits at the plugin seam rather than inside the shared operations because HTTP and import callers of those operations are already path-gated, and group import legitimately calls them at `capWrite`. `mah.kv` stays unguarded (plugin-private store). `TestPluginDBAdapterWritersCarryAWriteRoleGuard` fails the build if a writer lacks the guard. Guarded: Category, ResourceCategory and TemplatePartial create/update/delete at **admin**; NoteType, Series explicit create/update, relation types and relation **edges** at **editor**. Implicit Series creation through an ordinary Resource write stays at `capWrite`, matching the HTTP Resource surface. Edges are guarded even though `relationInScope` already confines them, because scope and capability answer different questions — "both endpoints are inside your subtree" is not an answer to "may you relate groups at all", and a plain user refused `POST /v1/relation` could otherwise make the same write through a hook its own upload fired. Consequently `relation_scope_test.go` builds a **synthetic scoped editor**, which no stored account can be (`normalizeScopeGroup` nils an editor's scope group): with a scope-limited *user* every assertion there would pass on the role guard and prove nothing about scope. `internal/arch/role_capability_gate_test.go` fails the build if a new operation of that shape appears without a guard; it enumerates the *read* prefixes rather than the mutating ones, so an unrecognised name (`BulkDeleteCategories`) fails instead of passing, and it strips comments at file level, because `stripGoComments` parses a *file* and silently returns a lone function fragment unchanged. Deliberately **not** guarded: Query and SavedMRQLQuery, whose operations nothing below `server/` calls — a guard there could not fire. What stays reachable to a confined or deny-all principal is anything `scopeColumn` does not map *and* no guarded operation covers: tags, which carry no owner. They stay reachable to a scoped *user* (`capWrite`) but not to a guest or the deny-all principal, see the next point. Relation *edges* are partly out of that set. Subtree containment for an edge is a property of two columns rather than one, so `EditRelation`/`DeleteRelationship` check both endpoints explicitly via `relationInScope`. Guarding the direct writes alone was worth little, because a relation type and a category both cascade to `DELETE FROM group_relations` database-wide, so there are two further layers: `refuseGlobalCascadeWhenScoped` rejects `EditRelationType`, `DeleteRelationshipType` and `DeleteCategory` early (before `before_category_delete` fires), and a GORM delete callback (`globalCascadeDeleteCallback`) refuses an ORM delete against `categories` or `group_relation_types` **issued through a handle that carries the scope filter**. It keys on the handle rather than the principal because that is the tree's doctrine — scope rides inside the `*gorm.DB` — which also means it does *not* cover a writer built once at startup from the singleton handle. `CategoryCRUD()` is exactly that, so the callback could never fire for it however `server/routes.go` were wired (only its `ListHandler` is routed today in any case). Per operation it is a real backstop for `DeleteCategory` and `DeleteRelationshipType`, whose cascades are transactional, and contributes nothing to `EditRelationType`, whose own write is an UPDATE. `UpdateGroup` additionally refuses a group the caller cannot see, before its hook runs: its scoped UPDATE matched no rows for an outside id but `RowsAffected` was never consulted, and the relation cleanup after it is keyed on the caller-supplied id — so a hook could delete the constrained edges incident to a group it controlled neither endpoint of.

**Two paths remain open and are known, not closed** (item 4.1 closed the first of the three, and corrected the reasoning about the second): deleting a group deletes every edge incident to it in both directions, far endpoint irrelevant (`deleteGroupInTransaction`'s `Select("...", "Relationships", "BackRelations", ...)`) — accepted, because the principal legitimately controls the near endpoint; and `AddRelationType` writes `BackRelationId` onto an *existing* reverse type it finds, so "create touches no existing row" is not true (it cascades to no edge, but it is a write). **Neither is closable with a subtree predicate**, which the earlier wording claimed for the first two. `AddRelationType` is an UPDATE. And sparing an edge on group delete is not merely ineffective but wrong on both engines: SQLite has `PRAGMA foreign_keys = ON` and both association columns carry `OnDelete:CASCADE`, so the database re-deletes whatever is spared, while Postgres opens with `DisableForeignKeyConstraintWhenMigrating: true` and therefore has **no FK constraints at all**, so a spared row survives pointing at a deleted group and `GetGroup`'s preload hands back a nil endpoint. Refusing the delete instead was rejected: it is an existence oracle (it tells a confined caller that an edge to an invisible group exists, which `relationInScope` and `GetRelation` answer with `ErrRecordNotFound` precisely to avoid) and it is unresolvable by the person who hits it, since a scope-limited user can see neither the edge nor delete it.

The group compare loader (`getGroupForCompare`) confines `Relationships` and `BackRelations` by far endpoint through `visibleGroupIDs` in Go (`confineGroupEdges`), like `GetGroup`'s `relCond` but without an `IN (<subtree ids>)` preload predicate; it is inert for unscoped principals.

Changing a group's own category **is** closed: `deleteRelationsSparingUnseen` (`group_crud_context.go`) selects the edges incident to the group, filters their far endpoints through `visibleGroupIDs` in Go, and deletes by explicit edge id. It spares an edge reaching outside the subtree rather than refusing the write. What that leaves is a row whose category no longer matches its relation type — a create-time check in `AddRelation`, never enforced at read time, and one `MergeGroups` already produces routinely by copying edges with no revalidation; an inconsistent row an editor can repair beats an edge nobody can restore. The select-then-delete shape is deliberate: appending an `IN (<subtree ids>)` predicate is what `visibleGroupIDs`' own comment rejects, since the allow-list can exceed SQLite's and Postgres's parameter ceilings, whereas one group's edge degree cannot. For an unscoped caller `visibleGroupIDs` reports every id visible, so the branch is inert. A fourth, group merge's final `DELETE FROM group_relations WHERE to_group_id = from_group_id` sweep, was closed and now carries the subtree filter when the merge is scoped. The general case — a confined caller performing an admin-only taxonomy write — is closed by the role guard described above. `mah.db.mrql_query` is the one data path that bypasses `BindInvocation` (it has its own executor), so it carries the actor on `MRQLExecOptions` and binds through `WithMRQLPrincipal`, resolves SCOPE via `ResolveMRQLScope` and clamps with `effectiveMRQLRequestedScope` — a plugin asking for `scope = "global"` still gets its caller's subtree. Only a `uint` crosses into `plugin_system`; `internal/arch/plugin_auth_import_test.go` keeps it that way.

**Descriptions and note text blocks are sanitized under auth, for every role** (#92). Raw HTML in markdown is allowed on purpose (KAN-4), and with auth off it still renders as written. With auth on, accounts less trusted than an admin write that text and an admin reads it, so raw HTML there would make every writing role script-equivalent to admin: one page view runs the writer's script with the viewer's session and CSRF token. Every path that renders a Description or a text block therefore passes the `markdown2 | render_mentions` output through `sanitize_under_auth:authEnabled` (`server/template_handlers/template_filters/sanitize_filter.go`): `partials/description.tpl`, `partials/renderedTextBlocks.tpl` (the note page and `GET /v1/note/renderedTextBlocks`), `displayNoteText.tpl`, `POST /v1/<entity>/previewDescription`, and the share server's `shared/displayNote.tpl` and `partials/blocks/sharedBlock.tpl`. It applies to admins' own text too: the role of the reader, not the writer, is what is at stake, and a stored Description outlives its author's role. The filter is an allowlist over `golang.org/x/net/html`'s parse: elements not listed are unwrapped and the code-bearing or re-parse-unstable ones (`script`, `style`, `template`, `noscript`, `iframe`, `object`, `svg`, `math`, form controls and the rest of `dropRaw`) are removed with their content; attributes not listed are dropped, which removes every `on*` handler and every Alpine directive (`x-*`, `@*`, `:*`), since both render paths run Alpine over the content; `href`/`src`/`cite` must be relative or `http`, `https`, `mailto` (plus `data:image/{png,gif,jpeg,webp}` in `<img src>`); `class` keeps only `language-*` and `mention-*`, so stored text cannot borrow the page's utility classes to overlay it; `style` survives only as goldmark's table `text-align`. The filter runs **before** `process_shortcodes`, so shortcode output, which is the application's own markup (Alpine included), is not stripped. That ordering means a shortcode written inside an attribute would expand after the URL check, so `[` and `]` in attribute values are written as `&#91;`/`&#93;` and do not parse as shortcodes there; in text they are untouched. The filter's parameter fails closed: only an explicit `false` skips it, so a render context that forgets `authEnabled` sanitizes. Because shortcode output is not checked, a shortcode in that text must not emit stored data unescaped: `[property path="Description" raw="true"]` would otherwise put a Description's own `<img onerror>` back after the sanitizer removed it, and `Name`, Meta (`[meta inline raw]`) and `[each]`'s `[item raw]` work the same way. Those two templates therefore pass `untrusted=authEnabled` to `process_shortcodes` (and the preview handler sets it), which sets `MetaShortcodeContext.UntrustedSource`: `raw="true"` is then ignored on `[property]`, `[meta inline]` and `[item]`. The flag follows the render everywhere it goes: into `[mrql]` and `[using]` result contexts (an `[mrql]` body or a Category's `CustomMRQLResult`/`CustomCSS` reached from user content), and into the deferred token (`deferredtoken.SealWithTrust`) of `[lazy]`, `[details]`, `[autorefresh]` and the `[reload]` region, so `/v1/shortcodes/deferred` renders those bodies the same way. Every other built-in handler escapes entity data unconditionally. Plugin shortcodes emit their own HTML and are not covered (#106). Category, Resource Category and Note Type templates (`CustomHeader` and friends) are not covered; they are admin/editor-gated and stay raw. There is still no Content-Security-Policy on the primary server (see `withPrimarySecurityHeaders`). Tests: `server/api_tests/stored_html_under_auth_test.go`, `server/template_handlers/template_filters/sanitize_filter_test.go`.

**Private storage is reserved by one predicate, at every reader of a stored location.** The storage root also holds application-private files: `_exports/` and `_imports/` (group archives), `_plugin_commands/` and the configured staging root, and `_job_replay_key`, which decrypts every stored Job replay envelope. `MahresourcesContext.IsPrivateStoragePath` (`application_context/private_storage_path.go`) decides what is reserved: the name half, `storage.IsPrivateRootName` (any top-level entry starting with `_` or `.`, after separator and dot-segment normalisation), needs no configuration; the physical half resolves the path under its mount, following symlinks and comparing case-insensitively, against the configured private roots, so an alternate filesystem or symlink that lands inside one is reserved too. The raw file server (`guardedFileServer`) answers it with 404 for every role, admins included. A resource row addresses a file by its stored `Location`, so the same answer is applied wherever a row is turned back into a file: `StoredLocationIsPrivate` (which also refuses any `..` segment) gates `AddLocalResource` before its dedupe lookup, `GetVersionFileHandler` (404) and `removeIfUnreferenced`, which never removes or backs up such a file; group export's blob pre-scan reports one as a missing blob (so the manifest never promises it) through the configuration-free `storage.IsReservedLocation`, because `groupio` cannot see the configuration. `POST /v1/resource/local` itself is **admin only**: registering a server-local path reads any file under the root, outside every subtree, so it is listed in `isSystemPath` and `AddLocalResource` carries `requireAdminRole` for callers below `server/`. The offline importer (`cmd/importExisting`) binds no principal and is unaffected. `TestResourceFromLocalRefusesPrivateStorageAndNonAdmins` pins the HTTP behaviour; `TestAddLocalResource_RequiresAdminAtTheOperation` and `TestAddLocalResource_RefusesPathsResolvingIntoPrivateRoots` pin the operation, and `TestStreamExport_PrivateStorageLocationIsNeverArchived` pins export.

**Only an admin moves a scope group.** Assigning a user's scope group is admin-only (`/v1/user*` is `capSystem`). Deleting a group that is some user's scope is refused with `ErrGroupIsUserScope` (**409**) for every caller. `MergeGroups` moves scope references from the losers to the winner, so a merge never orphans a scope, but only for an admin or a context with no principal (the system). Any other principal, a scope-limited user or an editor, gets `ErrGroupIsUserScope` (409) when a loser is a user's scope. The check runs under the user-management lock and the loser row locks, before any transfer or `before_group_delete` hook. The refusal tells a confined caller that the group is some account's scope, which a delete already reveals.

Passwords have a minimum length (`auth.MinPasswordLength`, currently 8), enforced on user creation, password change, and `-create-admin-password` bootstrap. Existing accounts are not re-validated on login. Bcrypt's 72-byte input limit is enforced rather than silently truncated.

Login serialization: `AuthenticateAndCreateSession` verifies the password **outside** any transaction, then re-reads the user under the shared user-management lock and refuses to insert the session unless the stored hash still matches the one it verified. A reset, disable or delete that commits first changes or removes that hash so the session is never minted; one that commits after deletes it. Keep the bcrypt compare out of the locked transaction — holding a process-wide lock (on SQLite, the database writer lock) across ~45ms of hashing lets unauthenticated login traffic stall every writer in the process. If minting the session cannot claim the lock within `loginLockWait` (a transaction-local `lock_timeout` on Postgres, where the advisory lock would otherwise wait forever; on SQLite the writer lock is already bounded by the connection's `busy_timeout` and `loginLockWait` is ignored), the login returns `ErrLoginUnavailable` → **HTTP 503** with `Retry-After` (`/login?error=busy` for the browser form).

Login request bodies (`POST /login`, `POST /v1/auth/login`) are capped at a fixed 64 KiB before credentials are read, independent of `-max-json-body` and Content-Type; an oversized request returns 413 without being charged to the limiter.

Only a **verdict on the credential** — `ErrInvalidCredentials` or `ErrUserDisabled` — is answered with 401 and charged to the login rate limiter. The current-password check on `POST /v1/account/password` is also a credential verdict: it runs through the same limiter (`credentialAttemptGuard`, injected into `api_handlers` because that package cannot import `server`) and the same `ip:`/`user:` keys, so a wrong guess there counts against login and vice versa, a success clears the account's failures, validation and database errors are not charged, and a throttled request gets 429 before any bcrypt work. Contention gives the 503 above; every other failure (dropped connection, exhausted pool, failed random read, and any error type added later — `classifyLoginOutcome` defaults this way) gives **HTTP 500** (`/login?error=unavailable`) plus an error entry in the application log, and is likewise not charged. Reporting an outage as "invalid username or password" both sends the user to reset a password that still works and spends one of their attempts. The credential read in `AuthenticateUser` runs before the transaction opens, so its errors are mapped separately from the transaction's — a contended read is still a 503, not a 401.

CSRF: the session cookie is `SameSite=Lax`, which blocks cross-site state-changing (POST/PUT/DELETE) requests; API-token (Bearer) requests carry no ambient cookie and are not CSRF-exposed. Layered on top of that baseline is a per-session synchronizer token (defense-in-depth): each session carries a random `Session.CsrfToken`, published to the page in a `<meta name="csrf-token">` tag and on `/v1/auth/me`. State-changing, cookie-authenticated requests must echo it via the `X-CSRF-Token` header (the JS `fetch` wrapper adds it automatically), a `csrf_token` urlencoded form field, or a `csrf_token` multipart field (native upload forms, as the first part; see below); the `withCSRFProtection` middleware rejects mismatches with 403. The check is a no-op when auth is disabled, and skips safe methods, login (`/login`, `/v1/auth/login`: no session exists yet), read-via-POST endpoints, and Bearer requests. Logout is checked: `POST /logout` and `POST /v1/auth/logout` need the token, and `GET /logout` only renders a sign-out form, because `SameSite=Lax` sends the cookie on a cross-site top-level GET and a GET that ended the session let any page sign a person out. The token is no longer accepted as a query parameter, because URLs reach access logs, proxies and history. For a multipart body the middleware peeks at most 4096 bytes, parses only the first part, and accepts it only if that part is named `csrf_token`; the peeked bytes are spliced back in front of the unread body, so the handler and its `MaxBytesReader` limit see the whole stream and a huge file is never buffered to find the token. `src/csrf.js` prepends (or moves up) the hidden input on native multipart submits, so the token is always first; a token that follows a file part is not honoured and gets a 403. JSON bodies are never read, and `fetch`/XHR callers use the header.

**Template Revision history is gated like the editor, reads included.** The edit pages of Categories, Resource Categories and Note Types are deliberately readable by lower roles, and the generic path rules give taxonomy and editor GETs only `capRead`, so prefix coverage would have left `GET /v1/category/revisions...` open to everyone, and with it every template a past author meant to remove. `templateRevisionCapability` (`server/authz_policy.go`) is consulted before those branches and classifies `/v1/<carrier>/revisions[/...]` and the reserved History page `/<carrier>/revisions` (the `.json` and `.body` variants normalise away) as `capTaxonomy` for Categories and Resource Categories and `capEditor` for Note Types, for every method. It reads the same `templateRevisionCarriers` table the router and the OpenAPI registry read, so a carrier cannot be routed and left ungated. The operations check again (`requireTemplateCarrierEdit`: list, get, diff, label and restore), because a plugin hook or any caller below `server/` never sees the path rule. `TestTemplateRevisionRoleMatrix` pins every role × carrier type × operation cell.
