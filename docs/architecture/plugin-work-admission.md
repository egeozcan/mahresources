# Plugin work admission

A plugin's VM runs one Lua call at a time, so a plugin makes progress on one piece of background work at once — and an execution that took shared capacity *before* it waited for that VM turned one plugin's backlog into held slots every other plugin and Kind waited for. So every async execution of a plugin (a registered action, a `mah.start_job` closure, a scheduled occurrence) takes, in this order, its **plugin's lane** (`plugin_system/action_lanes.go`: one FIFO per plugin name, a place taken synchronously at submission so work starts in submission order), then one of the process's `maxConcurrentActions` **job slots** and the plugin's **VM** together (`acquireSlotAndVM`: it never waits for one while holding the other), and then the **host's admission** (`HostJobRef.Admission`: the durable claim, against `max-job-concurrency`). The VM comes before the claim so a slot of the budget is only taken by work that starts at once — an action behind a long synchronous call into its plugin holds no slot of either kind — and a full budget gives the slot and the VM back before it waits, so hooks and pages are never held behind the budget. A disable revokes a VM without taking its lock, so liveness is checked again after the claim (`asyncWork.live`, in `cannotEnter`, which also refuses once the manager is closing); a claim granted into a revoked VM does not enter it, and the host is told the execution did not start (`HostJobSink.NotStarted`): a registered action's claim goes back to the queue, a closure or occurrence is withdrawn as not started. Neither is a failure. Waiting holds nothing durable; a plugin's backlog is `queued` Jobs behind one running Job (per process: each process has its own VM, and its claimed Job runs there). Every wait — the VM wait included, through a context — also ends when the VM the work belongs to is revoked (`stateRevoked`), so a disable does not wait out the drain for queued work that could never run, and a head waiting on a revoked VM behind a long synchronous call does not hold the lane from the plugin's next VM. A schedule tick `joinAhead`s: its wait is bounded and it recurs, so behind a backlog it would give up at every tick; ahead of it, it waits only for the running handler — but never twice in a row while an action waits, or an overrunning "allow" schedule would starve submitted work.

- **A bounded caller's deadline reaches the admission** (`Admit(deadline)`). The host puts it on the claim's *database handle*, never on the context `ClaimJob` builds the `Execution` from: an Execution publishes through the context it was claimed with for the rest of its run, so a deadline there silently drops every output published after the dispatch wait. An admission that returns after the deadline is not run; the host withdraws the claim it granted. `TestAnOccurrenceAdmittedUnderADeadlinePublishesAfterIt` fails if the deadline moves to the context.
- **A write that ends a Job this process has given up is retried until it lands** (`settlePluginActionWhile`): a refusal under a fresh claim, and the withdrawal of a closure or occurrence whose callback was lost before its claim. Nothing else would end either — no execution holds it, and while this process lives no other one can prove its work is gone. A refusal made under a claim is recorded after the VM is released (`endClaimed`), never while holding it.
- **One deadline covers everything an admission does with the VM held**: the claim, the read of the claimed input, and the re-checks of the acting principal (`pluginActionAdmissionAttempt`, or the caller's deadline if earlier). The re-checks return `(reason, error)` (`pluginActionRefusalWithin`, `commandActorRefusalChecked`): a read that failed or ran out is an error, never a refusal, because each of those reads already fails closed and would otherwise block a Job as `role-refused` or `target-out-of-scope` over a slow query. The scoped context is built on the bounded parent (`withPrincipalWithin`), never given it afterwards: the scope rides on the handle's `Statement.Context`, and `WithContext(bounded)` would silently drop it. `jobs.ClaimJob` reads the input, and blocks a Job that cannot run (principal gone, input unopenable), on the claim's bounded handle, and never drops the claim it took: a failed input read answers `ErrExecutionNotLoaded` *with* the claimed execution (the admission then runs with the input it queued with, the same sealed content), and a block that could not be written answers an `*UnrunnableClaimError` with it (the admission records the block itself, retried, and never runs it). The Execution still publishes through the context `ClaimJob` was given, and `ClaimRequest.Claimed` names the claim to its caller the moment it commits, so the admission's own panic recovery can end a Job whose post-commit work panicked instead of returning.
- **A "skip" schedule's deadline is asked again once everything is held.** A lane turn, a job slot or the VM that is free when asked for is taken without waiting, so a run could otherwise start after its dispatch deadline on resources that never made it wait. `runAsyncJob` checks the absolute deadline (`asyncBounds.slot`) after the slot and the VM are held and gives them back past it; an admission granted after it is withdrawn by the host with a retried write (`settleUnstartedOccurrence`). An "allow" run has no absolute deadline, only a bound on its slot wait, so a free slot is still taken there (`TestOverlapAllowWaitsOutABusyVM`).
- **Nothing runs on a re-check that did not answer.** When the re-checks under a claim cannot answer, the admission hands the claim back (`giveBack`: `ReleaseClaim` to `queued` under its own token, retried off the VM path, heartbeat stopped once it lands) and answers `AdmitDeferred`, whatever an earlier attempt found. The lane head then steps out (`stepOutOfLane`): it gives its place up, so the plugin's other work runs, stays out for the admission's `Deferral` (one second, doubling with each give-back in a row up to `pluginActionGiveBackCap`, 30 s), and rejoins at the back. After one give-back, later attempts ask the re-checks *before* claiming (`checksAnswerBeforeClaim`, as the principal the claim would read: `waitingExecutionAccess`) and defer again, with the same growing deferral, while they still cannot answer. `started` and `queued` are host lifecycle events that no timeline ceiling bounds, so without this a failure lasting a day wrote thousands of them; now a failure streak writes one pair. The re-checks under the claim still decide. A check that is slow but answers (a scope subtree of a very large deployment) is not stalled for good: each attempt's bound doubles with the give-backs before it (`attemptBound`, up to `pluginActionAdmissionAttemptCap`, one minute), so it eventually fits while no attempt holds the VM for longer than the cap. Before a claim is given back the Job's progress says "Waiting for the account and scope checks" (a snapshot, not an event), so the queued row says why; the start that ends the wait replaces it. That write is best-effort and bounded (`pluginActionWaitingNoticeBound`), because the release it precedes is what frees the Job's slot of the budget. Until a given-back claim lands the admission answers `AdmitDeferred` again (`stillReturning`), because the Job is still running under the returned token and a claim asked for then would read as another runtime's; the execution stays out of its lane meanwhile rather than holding it from the plugin's other work. What the admission did under its own claim is known without reading the Job, so `settleUnstartedOccurrence` and `CallbackLost` act on it (`endedByItself`, `afterReturn`). `TestAReCheckThatCannotFinishGivesTheClaimBack` (and its Postgres twin), `TestAReCheckThatKeepsFailingBacksOff` and `TestAFailedReCheckNeverRunsTheJob` drive it with a GORM callback that stalls or fails one read.
- **A failure path never turns an unread result into a verdict.** A read that failed is indeterminate: it is retried or passed up, never taken as "absent", "false" or "refused" (`pluginActionNeverStarted` answers an error, and `awaitPluginActionRun` asks again). A write that must land to end or return a Job is retried until it lands or the Job has left the state it was written for (`settlePluginActionWhile`, `retryPluginActionSettlement`), including an unstarted occurrence's withdrawal and the read of where it stands (`settleUnstartedOccurrence`). A claimed execution is never dropped without a fenced release or block.
- **"It ended" is not "it ran".** A withdrawn Job is `cancelled` with a `not-started` event; `awaitPluginActionRun` reads that event (`pluginActionNeverStarted`) so a scheduler waiting on an occurrence another runtime gave back does not record a completed run.

- **Plugin-action Jobs are accepted `queued` and claimed at the head of the lane** (`application_context/job_plugin_action_admission.go`). A full budget answers `AdmitLater` (`jobs.ClaimJob` returns `ErrCapacityExhausted`, which `Claim` folds into "not claimed") and the head asks again every `hostAdmissionPollInterval`; a Job that is no longer waiting (`ErrJobNotWaiting`) is `AdmitWithdrawn` and leaves quietly. Re-validation (`pluginActionRefusal`, the schedule's actor refusal) runs under the fresh claim, so a request and a Retry are checked when they run. `mah.start_job` therefore never raises for a full budget.
- **The dispatch loop does not claim this Kind** (`RuntimeClaimEnabled() false`): it claims the oldest waiting Job whatever its plugin and would then wait for that plugin holding the claim. Its cadence instead runs `AdoptWaiting`, which hands this process's lanes the waiting Jobs nothing here holds — Retry and Continue successors, work a stopped process left queued, another process's overflow — idempotently (`HostJobHeld`, and `RunActionAsyncForHost` answers the existing entry for a held Job), and only while the plugin's lane is shallower than `pluginActionAdoptDepth`: every process adopts from one queue, and filling lanes with the whole backlog would hold a goroutine and an entry per waiting Job in every process. A queued action is re-resolved when it starts (`resolveQueuedAction`: same filters, same entity kind, params that still validate), because a plugin can be reloaded while it waits. **A closure is never adopted**: its `*lua.LFunction` lives in one process, so a waiting closure is withdrawn only once its runtime is provably gone. **Nor is a fresh scheduled occurrence** — it belongs to the scheduler holding its row's claim, which records its outcome; a run elsewhere would leave the row to fire the same interval again. Only a Retry's successor (it has lineage ancestors) is adopted. It holds no row claim, so it waits for its plugin and the budget without a bound (`runQueuedScheduledOccurrence`), and one this process does not start stays queued or has its claim returned, as a queued action's does (`waitsForAnyProcess`): no next interval would run it instead. Work for a plugin not loaded here is left for a process that has it, and ended (blocked or failed) only when the deployment's `PluginState` has the plugin disabled: not having it loaded here proves nothing. For the same reason a Job this process accepted but could not hand to its lane (the plugin stopped, the manager is closing) stays queued rather than being failed or blocked. An admission's database work is bounded (`pluginActionAdmissionAttempt`) even for an unbounded caller, because it runs with the plugin's VM held. A scheduler whose own attempt did not start reports an occurrence another runtime ran as its run (`settleUnstartedOccurrence` reads terminal Jobs through `awaitPluginActionRun`). Before admission a lost callback means: a registered action stays queued for the next process, a closure or occurrence is withdrawn as never started.
- **Plugin commands and imports wait too.** `claimPluginCommandJob` surfaces `ErrCapacityExhausted`, `SubmitCommandJob`/`SubmitImportJob` translate it to `plugin_commands.ErrJobCapacityFull`, and the dispatcher puts the run or import back at the head of its plugin's queue and pauses starting anything for `jobCapacityRetryDelay` — a wait, never a `RunStatusFailed` "not claimable". The six-entry managed lane they run in is the same kind of wait: an entry leaves only when its callback returns, which can be after the budget it held has freed, so both ask `ManagedLaneHasRoom` before claiming and answer a full lane as `ErrJobCapacityFull` without taking a claim. A lane that refuses after a claim anyway (`download_queue.ErrManagedLaneFull`) gets its claim given back, retried until it lands or the command fence is gone (`refusedByManagedLane`), and the same wait. Runs and imports take turns for room (`dispatcherState.importsFirst`): the kind just started goes second next time and a kind refused keeps its turn, so a replenished run backlog cannot take every freed slot while an import waits.
