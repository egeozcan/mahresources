# Plugin downloads and media

Two plugin surfaces built on the host work in [HLS ingest](hls-ingest.md) and [Host fetch](host-fetch.md): `mah.download.submit`, and `mah.media`.

**`mah.download.submit(url, opts)` is gated on `CapDBWrite`, deliberately not on a name of its own.** The power is `create_resource_from_url`'s — fetch a URL of the plugin's choosing into the library, which that capability's label already states — differing only in whether the caller waits. It is not `CapJobs` either: `jobs` means a plugin's *own code* runs in the background, and none of it runs here; the host downloads. What it buys is the two things a synchronous fetch cannot give, since `create_resource_from_url` holds the plugin's VM lock for the length of the transfer and, inside an async job, dies at `MaxAsyncJobDuration`. `internal/arch/plugin_capability_gate_test.go` pins the gate, so folding it under a different capability fails the build rather than silently widening what a `jobs` or `db:read` plugin can do.

- **The transfer runs under the *plugin's* declared network list, never the host policy**, which allows every public host. `DownloadJob.pluginName` selects it; `createHTTPClientFor` refuses when it cannot be resolved rather than falling back — an unresolvable plugin is one that was disabled, renamed, or whose resolver was never wired, and every one of those is a "no". The resolver is set through `SetPolicyResolver` *after* construction, in the `SetKVStore` shape, because the manager is built while the context is still assembling itself and a closure passed through `ManagerConfig` would capture a nil plugin manager.
- **The origin is persisted on the history row** (`DownloadHistoryEntry.PluginName`) and carried on the upsert's update arm. A retry replays the stored payload on a fresh worker, possibly in a process that never saw the job; one that forgot the origin would silently become a host fetch. Same doctrine as `validateDownloadScope`: a payload records what was once asked for, not a standing permission.
- **Layer (a) is checked at the call site too**, as `create_resource_from_url` checks it before creating anything. It is not the protection — the transfer is policed again when it runs — but the difference between telling the plugin now and letting it find out minutes later in a history row.
- **The targets are validated against the acting principal's scope**, mirroring `validateDownloadScope`, which cannot be reused because it takes a principal off a request and there is none here. Without it a plugin's Lua running on a confined user's own write could submit a download owned by a group that user cannot see, and the worker would create it. The worker now binds the submitter's account at create time as well (see "Deduplication counts only what the uploader can see" in [Bulk resource uploads](bulk-resource-uploads.md)), but that is a second line: it refuses the create after the transfer has been spent, where this refuses the submission. The principal is resolved from the actor id through `principalForPluginActor`, the same resolver `mah.db` binds through, so a deleted or disabled account is deny-all rather than unscoped.
- Refused inside `mah.db.transaction`: a queued download outlives the transaction waiting for it. The returned status comes from `job.Snapshot()`, not the live job: `Submit` starts the worker before it returns.

**`mah.media` is `CapMedia`, separate from `CapImage`.** `mah.image` transforms bytes the plugin already holds and touches nothing else; `mah.media` reads video and audio *out of the user's library* and spends an ffmpeg process doing it, so folding them together would silently widen every plugin already consented to image transforms — the widening `CompareGrants` exists to report.

- **The seam is deliberately not a new wiring point.** `mediaProcessorFor` reaches through `querierFor` — the function the whole `mah.db` surface goes through — and type-asserts what `BindInvocation` returned to `MediaProcessor`. Every call is therefore already bound to the acting principal, so a group-limited caller cannot probe or cut a resource outside its subtree: a property of the handle rather than of a check somebody has to remember. A seam of its own would have been a second path to the same files with none of that. A compile-time assertion on `*pluginDBAdapter` keeps the assertion from quietly starting to answer nil.
- **A plugin names a resource id and a number, never a path and never an ffmpeg argument.** `probe` returns the ffprobe document whole (`format` plus `streams`), because which field matters varies by caller and a curated list is one somebody keeps extending. `extract_frame` returns the `data:image/jpeg` URI `mah.image` already speaks, so the two compose without a conversion step.
- **`ExtractVideoFrame` is a sibling of `createThumbFromVideoFileAtTime`, not a caller of it.** That one exists to make a thumbnail, so it rounds the timestamp to a whole second and scales to a fixed 640px — right for a thumbnail, wrong for an API whose caller asked for a particular moment. It shares the video thumbnail lock and timeout, so plugins cannot start more concurrent ffmpeg processes than the deployment already allows for the same work, and it falls back to documented defaults when those are zero: a context built from a bare config (the CLI, every test) would otherwise refuse every frame with a message about a timeout nobody configured.
- **Every ffmpeg-family call takes the deployment's video gate**, `probe` and `extract_frame` through `runVideoTool` and `trim` through `trimVideoGated`. Trim is gated *around* `TrimVideo` rather than inside it, because the bound belongs to the plugin surface — a person clicking the trim button does one at a time, a plugin loop does not — and moving it inside would change the HTTP endpoint too. It cannot deadlock: `TrimVideo` takes a different lock, and nothing beneath it takes this one, since thumbnails are generated lazily on request. It carries no run timeout, because a trim is a transcode and the thirty seconds that bounds a frame would refuse every clip over a few minutes.
- **Waiting for the gate is bounded by the caller's own deadline** (`videoLockWait`). The lock's wait takes no context, so a cancelled request or an expired async job would otherwise sit in it for the full configured minute doing nothing anybody is waiting for — a minute a schedule handler spends outside the budget its claim TTL is derived from.
- **The temp-file copy happens inside the gate**, under its deadline. On a filesystem with no local path, probing copies the whole file; doing that before taking a slot meant an unbounded number of concurrent copies, each able to outlive the caller's budget, and afero readers take no context so `cancelableReader` is where the question gets asked.
- **`runVideoTool` takes the gate first and derives its deadline second**, so a request that spent half its lock wait still gets a full execution budget — a deadline started before the lock is spent by the queue in front of the call, and one that waited the full lock timeout would hand ffmpeg a context already cancelled. It builds the command on that derived context rather than the caller's. That second half is the one that is easy to get wrong: `RunWithLockTimeout`'s run timeout bounds only how long *it* waits — it returns while the function keeps running — so a command built on the caller's context leaves a wedged ffmpeg alive with nothing holding a reference to it. `probe` had no gate at all at first, which made the cheapest call in the API the one with no bound on concurrent processes.
- **The write surfaces check the acting principal's *role*, not only its scope** (`requireWriteRole`, beside `requireTaxonomyRole` and `requireEditorRole`). `mah.media.trim` and `mah.download.submit` both write, and a plugin reaches them from a page a **guest** is entitled to read — a shortcode or an injection runs as whoever loaded the page, so the URL rule that refuses a guest every mutating endpoint is nowhere in the path. Scope cannot answer it either: the guest's own subtree is exactly where the write would land. This is the general form of the hazard [Authentication & roles](authentication-and-roles.md) already records for hooks, applied to two new doors.
- **All three are refused inside `mah.db.transaction`**, not only `trim`. Each waits up to a minute for a video slot, may copy the file, and then runs a process; inside a transaction that is the database's write lock held for the whole of it, and a read that takes a minute is as bad as a write that does.
- **`trim` takes an `into` of `"version"` or `"resource"`.** The default replaces the resource's content, as the trim button does; `"resource"` files the clip separately and leaves the source alone, which is what a plugin pulling five clips out of a recording needs. `trimVideoBytes` is extracted so both share one definition of what the clip is, and `parseTrimRange` so they cannot drift on what a valid range is. An unrecognised `into` is refused rather than defaulted: a typo that quietly replaced a two-hour recording with a ten-second clip is not something an author finds out about in time.
- **ffmpeg and ffprobe get a real file, never a pipe.** Both need to seek, and an MP4 whose `moov` atom sits at the end cannot be read from stdin at all; `localOrTempPath` hands back the file itself on a local filesystem and copies to a temp file on any other, which costs a copy and always works.
