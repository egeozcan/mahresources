# Plugin handler stops and outcomes

The host ends a running async handler through one mechanism: the handler's Lua context is cancelled with a cause (`plugin_system/action_handler.go`). gopher-lua checks its context between instructions, and `mah.sleep` and `mah.http` wait on it (the stop is what `vmRequestContext` answers inside a job), so a handler stops at its next step after a Go call returns. The 5-minute timeout always worked this way, so a handler that cannot survive being stopped between two instructions was never safe to run. Three causes use it: a person's **Cancel** (`StopCancelled`), a **disable** (`StopPluginDisabled`, from `finishTeardown`, only for handlers whose VM `live()` no longer answers, so a re-enabled VM's handlers are untouched), and a **shutdown** (`StopRuntimeStopping`).

- **An execution is in flight from its submission until its goroutine has settled it**, and every walk that stops, waits for or reports executions goes through that registry (`trackExecution`, `inFlight`), never through `actionJobs`: that is the panel's list, and a handler that called `mah.job_complete` and kept working reads as finished there, so a person clearing it hid a live handler from the disable and the shutdown. An execution that leaves its lane unstarted because its VM went away or the manager is closing reports its own lost callback (`abandonUnstartedJob`, claimed under the job's lock like the shutdown's).
- **One execution reports one outcome.** `handlerRun.Unlock` records `settlesItself` under the job's lock *before* it releases the VM, and `reportLostCallbacks` claims `lost` under the same lock only for executions that neither settle themselves nor already reported, and never for one whose handler is still inside its call (`job.handler` set): nothing proves that call has ended, and a Job ended while it may still act could be retried beside it, so its Job stays claimed under this runtime until the handler returns or the next process proves this one gone. An execution reported lost reports nothing afterwards. The old order reported the outcome after the VM unlock, so `Close`, blocked on that VM, reached `reportLostCallbacks` while `Completed` was still publishing and recorded `interrupted` for work that had succeeded. `TestAnOutcomeBeingRecordedAtShutdownIsNotReportedLost` has a case whose settlement outlasts the wait, so it fails if the lock rule is removed even though `Close` also waits.
- **"It started" is decided at the handler's Lua call** (`handlerRun.enter`, which reports `HostEntryObserver.Entered`), not at `Started`: that report is a progress write, and a Cancel, a disable or a shutdown can land while it is made. `enter` asks the entry checks again (`handlerRun.refusal`: a pending cancel, a requested stop, a closed manager or a revoked VM) immediately before the call, and a refusal there, or an action that cannot be resolved because its plugin went away, is reported as not entered (`reportNotEntered`), exactly as the same refusal before `Started` is. The admission answers a waiting Run now from `Entered`.
- **`settleActionJob` classifies**: a status the plugin set itself wins (a declared completion or failure), then a handler that returned nil completed, then a handler the stop ended is `Stopped(reason)`, then a timeout (`errHandlerTimeout` as the context's cause) or an error is `Failed(HostFailure{Cause, Message})`. What ended the call is read from the call's own context (`handlerRun.ended`), whose cause is fixed by whichever came first: a disable that lands after the timeout ended a handler still inside a Go call does not turn its timeout into an interruption. The sink maps `StopCancelled` to `cancelled` and the others to `interrupted` with a failure naming the reason; a success refused with `ErrControlIntentWon` ends `cancelled`.
- **Shutdown is bounded** (`Close`): plugin `mah.http` requests are ended first (`httpCtx`, which their semaphore wait and their request both run under) and waited for at most `shutdownHandlerStopWait`; running handlers get `shutdownHandlerGrace` (5 s) to finish, are stopped, get `shutdownHandlerStopWait` (5 s) to unwind; a VM whose lock is still held after that is revoked and left open for the exit (`closeStateBy`), and outcomes still being written get `shutdownSettleWait`. Then the executions that will never finish are reported lost (`reportLostCallbacks`), which is the host's database write and is given up at the deadline; the next process resolves what was not reported. All of it is held to `shutdownBudget` (15 s): every wait before the reports ends by `shutdownBudget - shutdownReportWait` whatever its own bound, and the reports get the rest. Work admitted after `closed` is set does not enter its handler. Systemd's default stop timeout is 90 s, and the other drains (HTTP 30 s, commands 30 s, scheduler 10 s, the download queue's workers, generic jobs included, 5 s, and under `-memory-db` the queue executions still publishing an outcome, 5 s, before the scratch database closes) share it.
- **Cancel** (`pluginActionAdapter.cancelCommands`): every Job whose handler has not started (queued, or blocked/paused with no held or quarantined claim) is offered Cancel, which the host applies in the command's own transaction. A running Job is offered it only where the registration declared `cancel = true` (`ActionRegistration.Cancellable`, `ScheduleRegistration.Cancellable`), as the design's command matrix requires ("Cancel only when registration explicitly declares support"), and the declaration is read from the **Job** (`pluginActionJobInput.Cancellable`, copied into the summary), not from whichever process serves the command: two processes running different plugin.lua would otherwise let one authorize stopping the other's handler. The executor enforces the same fact (`HostJobRef.Cancellable`, `handlerRun.cancellable`), and a Job accepted as cancellable whose registration has since withdrawn it is refused at its admission (`registration-changed`). The process running the handler stops it from `ExecuteCommand`, or reads the recorded intent on its heartbeat (`deliverPluginActionCancel`, every second) when another process ran the command; a cancel that reaches an execution between its claim and its handler keeps the handler from being entered (`pendingStop`, `cancelledBeforeEntry`) and ends the Job cancelled. A claim whose handler was not entered is never returned to the queue with a won cancellation on it (`pluginActionSink.returnClaim`, used by a give-back after checks that cannot answer and by `NotStarted`): it ends the Job cancelled instead, because a queued Job whose checks keep failing would never reach the execution that ends it. A cancellation that lands as the release is written goes back to the queue with the Job, and the next admission reads it right after its claim (`cancelWon`) and ends the Job without asking the checks (`checksAnswerBeforeClaim` lets it claim). The writes that end or return an unstarted Job retry a version conflict (`settleRefused`) rather than treating it as final, since a recorded cancellation moves the version. A running Job whose handler has not entered yet is still offered Cancel only by its declaration: whether it entered is not a fact the command's transaction can read. `selectCancellable` is the same rule as one predicate, and `TestRegisteredKindCommandSelectorsMatchCommands` holds them together.
- **A failed plugin Job shows the plugin's reason**, redacted of the Job's own parameter values (`safeText`) and bounded.
- **A plugin's `password` settings are redacted from what the host itself publishes**, every occurrence, as `[redacted]` (`plugin_system/secret_redaction.go`). A handler receives them (`ctx.settings`) and can echo them. The scope is a decision, not a gap: the host redacts (a) everything it persists or shows on the **Job plane** for plugin work: the title (a registered action's label, a `mah.start_job` label, before both acceptance and the in-memory entry), progress text including its unit (a metric whose key would be redacted is dropped, as the durable plane drops it), metric labels and units, the failure (a handler's error, abort reason or `mah.job_fail`), the result, the timeline, the in-memory entry and its SSE events; and (b) **every log line it writes from a plugin error or a refused request**: the server log's plugin error lines, `mah.log` entries at `/logs`, load and `init()` failures (redacted before they leave `EnablePlugin`, so startup's log entry is too), and egress refusals. A synchronous action's answer (its error, abort reason and result) is redacted as well, since it is the same handler text a Job would show. It does **not** police a plugin's own direct output to its caller: page, slot, shortcode, block and display HTML, or an API endpoint's body or abort reason. Plugins are trusted code under operator consent; one that prints its key into its own page could equally inject a script (`CapInject`), and the host cannot tell a secret from a coincidence in deliberate output. The *errors* of those calls are still redacted (`pluginCallError`, which keeps `Unwrap`), because the host writes them. Identifiers (action and schedule ids) are code the author declares and are not redacted: naming one after the plugin's own secret is deliberate output, and redacting ids would break dispatch and replay. Redaction never changes meaning: the result keys the host interprets (`ResultProtocolKey`: success, message, redirect, job_id, data, continue) keep their names and only their values are redacted, and a `mah.log` level outside info, warning and error is logged as info rather than redacted. `safeText` applies the redaction again on the durable plane. The values are read before the lock the text is stored under: `pluginSecrets` takes `pm.mu`, and nothing takes it while holding a job's lock (`settleActionJob` works out the failure first). **Known limit:** redaction knows the *current* values, so a handler still holding a key the operator has since rotated is not redacted of the old one; after rotating a key, revoke the old one at its issuer. `mah.job_fail`/`mah.abort` are `plugin-action-failed`/`dependency`, a Lua error `plugin-handler-error`/`internal` (its first line, with the plugin's directory stripped by `handlerErrorText`, which only plugin_system can do), a timeout `plugin-handler-timeout`/`timeout`.
- **An interrupted Job may carry a failure** (the Service accepts one on `interrupted` as well as `failed`), which is how every surface shows why: a shutdown, a disable, or `runtime-lost` from reconciliation. A claim whose claimant is a runtime identity of **this boot session** that `Liveness()` proves gone is expired at once by `JobRuntime.tick` (`ExpireAbandonedClaims`, `runtimeClaimantGone`, which visits every held claim a page at a time, so a dead claimant behind a page of live ones is still found), so a crash does not leave Jobs reading as running for a whole lease; the Kind's own reconciliation still decides what they become. Another boot session is never early proof, because two machines can share a hostname.
