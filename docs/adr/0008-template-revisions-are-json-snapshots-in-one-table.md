# Template Revisions are whole-set JSON snapshots in one table

Categories, Resource Categories and Note Types record a Template Revision when they are created, when a save changes a tracked field, and on every restore. All three carrier types share one `template_revisions` table keyed by carrier type and carrier ID. Each row stores the carrier's whole tracked template set as one JSON snapshot, not one row per slot and not one column per slot. Revisions are written inside the same transaction as the save, under a lock on the carrier row, by the shared create and update functions (`CreateCategory`, `UpdateCategory`, `CreateResourceCategory`, `UpdateResourceCategory`, `CreateOrUpdateNoteType`). HTTP, CLI and plugin writes are therefore all covered without any of them opting in. Seeds, the Category a remote download creates by name, and the default Resource Category are created outside those functions and record no revision; a carrier with no revisions records its pre-save state as a baseline on its first changing save.

## Considered options

- **Per-slot history.** Each slot gets its own timeline. Rejected because slots depend on each other (`CustomCSS` styles classes that `CustomHeader` emits, `CustomHoverCard` falls back to `CustomSummary`), so restoring one slot alone can produce a set that never existed. Per-slot restore is still offered, as a whole-set snapshot whose other slots are current.
- **A table per carrier type, or one column per slot.** Rejected because slots are added often (seven in one release), and each addition would need a migration on the revision table as well as the carrier table. A JSON snapshot takes new slots with no migration.
- **Reusing the audit log.** `LogEntry.Details` is JSON, but log entries are pruned, unscoped to carriers, and today store no before/after state.

## Consequences

A snapshot taken before a slot existed has no key for it. Restoring that whole revision clears the slot, because a restore reinstates the exact state at that time; the diff shows the removal before the user saves. Snapshots keep each field raw, even when it is malformed, but a restore still passes the ordinary save validation: a revision that no longer validates is refused, and the user repairs it in the editor instead. Name, Description and MetadataIndexes are not tracked. Name identifies the carrier rather than describing its templates, and is unique for Categories and Resource Categories, so restoring it could collide. MetadataIndexes builds database indexes shared by every carrier of an entity type, so restoring it would reach beyond one carrier. Revisions are deleted with their carrier and are not carried in group export archives. Group import writes carriers without going through the shared functions, so it records the `import` revision itself.
