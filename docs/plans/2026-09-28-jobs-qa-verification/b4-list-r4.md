## Finding

### P1: a fetched drawer detail inherits the held progress version and rewinds newer progress

**Location:** `src/components/jobPanel.js:1052` in `loadDetail`, including the server-detail installation at `:1043`. The new marker is introduced by `src/components/jobProgress.js:407-409`; `mergeFetchedProgress` compares it at `:329`, and `progressVersion` reads it at `:19-22`. The correct removal rule already exists in `src/components/jobCenter.js:1101`, but this drawer detail path bypasses it.

`applyProgressFrame` deliberately leaves the lifecycle version and state alone while marking progress from a higher-version frame with `progressVersion`. That is necessary when the progress poll has reached a newer execution before the browser's lifecycle/detail read has caught up. A server snapshot does not contain that client marker. However, `loadDetail` first builds `{ ...row, ...state }`, inheriting the held marker, and only then sends that copy through `bounded`/`mergeFetchedProgress`. The comparator consequently attributes the server response's old progress to the newer frame's version.

**Concrete sequence:**

1. The drawer holds a running lifecycle-version-3 row showing 100/1000. Opening it starts a successful `/v1/jobs/a` detail read.
2. Before that response arrives, a version-4 progress frame reports 900/1000 at `2026-09-28T09:59:59.999999999Z`. The row correctly keeps lifecycle version 3, displays 90%, and records `progressVersion:4`.
3. The earlier detail response arrives with lifecycle version 3, 20/1000 at `2026-09-28T10:00:03Z`, and **no** `progressVersion`. It also carries a pin, phase and version-3 Cancel advertisement. Both the lifecycle-version and preference-epoch checks pass.
4. The raw spread at line 1052 attaches the held marker 4 to that version-3 response. The comparator now sees equal effective versions and lets its later timestamp win. `loadDetail` returns `read`; the drawer displays **2%**, while its row still claims `progressVersion:4`.

An earlier network response reaching the browser after a frame requires no failing or stalled DB call. Different execution clocks are expressly supported by the version-first contract; the higher-version/earlier-clock case is part of the refreshed required scope. Durable SSE lifecycle messages are event-only, so receiving the explaining event does not synchronously install the matching server snapshot before its progress frame. The drawer's separate bounded detail readers make this a real production entry point.

**Independent evidence:** `review-r4-consumers.mjs` imports the unmodified production components. It controls the promise returned by `requestJSON`, starts the actual `loadDetail`, delivers the real `handleProgressFrame`, then resolves the server response. A second case starts the actual opened drawer's `loadStaleDetails`/`startDetailReader` queue and reproduces the same result. The final log is `review-r4-consumers-final.log`, EXIT 1 with two failed scenarios for this **one** defect; its eight other scenario groups pass. Both cases finish all detail readers (`readers:0`, `inFlight:0`) before teardown. The root also independently reproduced the direct consumer and source inheritance, recorded in `root-r4-consumers-with-loader.log`.

The probe checks the cache as well as the row: `details.a` remains a genuine lifecycle-version-3 server copy with no marker, and its Cancel command still has `jobVersion:3`; pin and phase install correctly. The visible progress and `resultSource` read the row's progress, so that clean raw cache does not protect the bar. `progressValue(job)` returns 2; the drawer template binds that same value to both the visible percent and `aria-valuenow` (`templates/partials/jobPanel.tpl:158-164`). This is a wrong visible and accessible result, not just an unused internal field.

The damage can outlast the response: after the rewind, a valid version-4 frame showing 910 at `10:00:00Z` is rejected behind the falsely promoted `10:00:03Z`. A caught-up version-4 server snapshot showing 920 at `10:00:01Z` is also rejected. The lifecycle catches up to 4 and the marker clears, but progress still reads 20. Those consequences are recorded in the same final probe log; they are not additional findings.

**Suggested fix:** centralize the ownership of incoming snapshot metadata before any spread/merge. A server copy must be compared using its own lifecycle version and timestamp, without a marker borrowed from held progress; after comparison, retain the newer held progress and its marker where necessary. Route detail installation and other fetched snapshot construction through that same rule, including reducer copies and detail caches. The existing `mergeJobSnapshot` removal is evidence of the intended rule, but one caller is still constructing its own merged copy. Preserve the server's legitimate lifecycle, pin, phase, commands, outputs and preference-epoch semantics; assigning the frame's version to the whole row or discarding the entire response would change those contracts. Add coverage through the opened drawer's actual detail-reader path, with a higher-version/earlier-clock frame between request and response, then verify later valid frames and a caught-up snapshot remain admissible.

**Severity:** P1 under the supplied rubric: the round-4 common progress repair introduces a wrong user-facing result in a normal successful read/frame race. The two reproductions expose one missing incoming-snapshot ownership rule and are counted once.
