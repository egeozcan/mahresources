- **L7 is split.** You own the `/jobs` half: running rows freeze because `src/components/jobList.js` never listens for the canonical stream's `job-progress` frames (see how the drawer applies them in `jobPanel.js` `handleProgressFrame`). b4-detail owns the detail page half (the timeline, its paging past 100 events, and the phase after the end).

- Follow-up (P3, from batch 3): a download that finishes outside the drawer's capped finished group never reaches `trackResourceCompletion`, so it refreshes no resource list by itself. The newest downloads of a burst are inside the cap and one refresh re-reads the whole list, so decide whether it needs code or a documented limit.
- Follow-up (P2, from batch 3): when an administrator retries another account's failed Job, the owner's already-open drawer keeps the failure in Needs attention until its next list read, because the ancestor is unchanged and the owner cannot see the successor's events. Tell the ancestor's viewers without naming the successor (for example, a lineage event on the ancestor), or show why that can't be done safely.
- Follow-up (P2 perf, from b3-stream): an `owner=me` stream, like any non-admin viewer's, advances its cursor only on events it delivers, so every poll re-scans the other accounts' events above it. Advance the cursor to an allocator head read before each poll's events query; it needs its own tests (SQLite and Postgres) and must keep the reset rule (a cursor above the highest sequence ever issued).
