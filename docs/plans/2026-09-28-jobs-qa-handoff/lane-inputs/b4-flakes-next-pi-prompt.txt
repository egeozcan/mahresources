The issues this lane fixes (it owns tests, harness code, and minimal product fixes where a failing test exposed a real bug):

D1. Date boundary, timeline: the `mr groups|queries|resources timeline` doctests failed between local midnight and UTC midnight. Cause claimed: timeline buckets are UTC calendar periods, GORM stamps rows in the server's zone, and SQLite stores times as text in the offset given, so `created_at >= ? AND created_at < ?` compared wall clocks. Fix: `database_scopes.InstantRange` (models/database_scopes/db_utils.go) compares instants with julianday() on SQLite inside an indexed text window on the bare column; timeline_context.go routes all 12 bucket queries through it.
D2. Date boundary, Project Management "(overdue)": the task-date shortcode compared a note's due date (a wall-clock value parsed without a zone) with the date part of mah.util.now_iso() (UTC), and the board (pm-core.js) with new Date().toISOString(). Fix: new host function mah.util.today() (server's local calendar date), the Lua shortcode uses it, the browser code uses the viewer's local date (PMCore.today), a new time-log entry's default date too. The bundled plugin is mirrored byte-for-byte into e2e/test-plugins. Guard: e2e/tests/regressions/date-boundary.spec.ts runs its own server (TZ), browser (timezoneId) and dates in a zone a day away from UTC's at the moment it starts.
D3. Found by that guard on PostgreSQL: a note's StartDate/EndDate are parsed without a zone as UTC, but pgx returns timestamptz in the process's zone, so on PG they read back shifted, the edit form offered the shifted value, and every save (and the note API's partial edit, and plugin patch_note) moved them again. Fix: Note.AfterFind returns both in UTC, matching SQLite. Audit claim: no other person-entered date is parsed without a zone into a timestamp column.
