Jobs System QA Sweep

Eight agents each drove their own seeded instance of the jobs system for about an hour: the Jobs drawer, the Job Center at /jobs, job detail pages, every job Kind, the API and live streams, the mr CLI, legacy download routes, restarts, and multi-user access. Their 191 findings are merged here into distinct issues. All but two were reproduced at least twice by the lane that found them; the ones marked re-checked I reproduced again myself.

Remediation

The four remediation batches are complete. Batch 4 used Luna max implementation agents and independent Sol xhigh review subagents; every lane ended with a review containing no P0 or P1 finding. The final merged tree passed the Go, JavaScript, browser, CLI and PostgreSQL suites. Of 94 issues, 92 are fixed and two (A11 and K4) are documented limits.

Fixed beyond the list

  • Batch 1: once retention had deleted any Job a source mapping named, every later start of a retired database was refused. A missing mapped Job is now classified once, everywhere.
  • Batch 2: SQLite write transactions now take the writer lock at BEGIN. At 8 concurrent requests, group creates refused with "database is locked" went from 570–589 per 1,000 to none, and upload lock errors from 166–178 per 1,000 to 0 in 4,400.
  • Batch 2: an older Job whose account had been deleted ran with no permission check at all. It was found while proving that three race findings fail closed.
  • Batch 2: showing a plugin's own error text on its Job could have leaked a password setting. Review caught it before it reached master; password settings are now redacted everywhere on the Job plane and in the host's plugin log lines.
  • Batch 3: the long-running inline tag editor flake was a product bug. The Jobs drawer told every page to refresh its resource lists for downloads that had finished before the page loaded, which closed an open editor about a second after load (37 of 40 probe runs). Lists now refresh only for downloads that finish after the page was rendered.
  • Batch 3: a Job whose account was deleted just after it was picked up ended blocked, offering a Resume that could never work. It now fails, as it does when the account was already gone.
  • Batch 4: timeline buckets compare instants, Project Management dates use the local calendar, PostgreSQL note dates no longer drift on each save, and queue work drains before its database closes. A pause already held by the follower is confirmed from its durable Job; an expired command drain keeps owned process groups recoverable.
  • Ephemeral databases were never removed from /tmp (12,223 files, 21 GB on the test machine). They now live in a private directory and are swept once their owner exits.

Accepted limits

  • Near-duplicate image hashes ignore colour. Near-Identical is unchecked by default; a colour-aware signature requires separate schema and backfill work.
  • Summary-value searches over one million Jobs can take about one second on SQLite and three seconds on PostgreSQL.
  • The drawer’s capped reads can miss the soonest scheduled Job above 50 active Jobs, or a resource refresh for a download outside its Finished read.
  • A few races between an administrator deleting an account or changing a scope and a Job starting. Each fails closed; the Job shows a less precise reason.
  • Older Jobs whose account was deleted before this release. The upgrade notes give the query and the procedure, and migration readiness now lists them for review.
  • Plugin secret redaction knows current setting values only, so revoke a key after rotating it. A plugin's own page or API output is not redacted.
  • Two server processes whose clocks differ can miss, or add, one resource-list refresh around a page load.
  • During a rolling upgrade, pausing a download that an older process is running reads "Pausing" until the transfer ends. Cancel still works.
  • A filesystem delete that stalls during retention can remove a re-run's new export. A tab can miss a database restore once new events pass its position.

Fix first

P1 means broken, a security or data problem, or a task that cannot be done. Two are access-control leaks, two stop the server from restarting or run scheduled work at the wrong time, two starve or kill background work when job capacity runs out, and two lock screen-reader and high-contrast users out of what the drawer says and where focus is. All eight are fixed on master (batch 1).

What held up, and what this setup could not reach

Checked and fine

  • No markup injection on any surface: plugin labels, progress messages and units carrying <script> and onerror rendered as text in the drawer, /jobs, detail pages, plugin pages, /logs and the admin overview.
  • Per-role visibility of jobs, events, outputs, summaries, summary exports and the CLI; badge counts and hand-typed owner or kind filters never widen it.
  • Another user's job id and a nonexistent id get identical 404s on every canonical and legacy route, so there is no existence oracle. Other users' export and summary files are refused.
  • CSRF enforced on the 13 job endpoints tried; the v2 live stream closes or re-filters when access changes.
  • Long-running jobs are announced once with their failure reason, progress is not chattered, and reconnects are announced once each way.
  • axe (WCAG 2.2 AA) on the drawer, /jobs and detail pages: no contrast failures; no horizontal scroll at 320 to 1440 px; the drawer opens in 56 to 98 ms with up to 80 rows.
  • Retry leaves the source job untouched and links the successor; canonical ids stay immutable while the legacy handle follows the retry leaf.

Original sweep: not covered, or caused by the test setup

  • Real screen readers (semantics were checked through Chromium's accessibility tree and a live-region log), Safari and Firefox, Postgres, multi-process deployments, and session expiry by TTL.
  • Setup artefact: the demo heartbeat schedule called os.time(), which the plugin sandbox does not provide, so it failed every 2 minutes until 14:55. Those failed rows are noise; the "cancelled on every tick" behaviour it exposed is real (see the schedules issue).
  • Setup artefact: the start script first waited only 10 s for the old server to exit, so one restart briefly ran two processes on one database. Findings from that overlap were discarded.
  • Partly setup: in-memory files with a persistent database made plugin commands unusable after a restart. Kept as an issue because the documented default for that combination is what breaks.
  • All downloads came from one local host, which exaggerates how alike their titles look, but the title rule itself is the issue.
